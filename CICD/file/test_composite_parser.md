### **【文件角色摘要】**

*   **📌 主要功能與責任：**
    此文件是 `CompositeParser` 的單元測試集。`CompositeParser` 是實現「自然語言轉 SQL (NL-to-SQL)」功能的**核心協調器和策略管理器**。它本身不執行具體的解析邏輯，而是管理一組子解析器（如規則解析器、AI 解析器），並根據預設策略選擇最合適的一個來處理用戶輸入。此測試文件的核心職責是：
    1.  **解析器管理**: 驗證 `CompositeParser` 能否正確地添加、移除和管理實現了 `IParser` 接口的子解析器。
    2.  **策略驗證**: 測試其核心的解析策略。這包括如何評估每個子解析器的處理能力 (`can_handle`)，如何根據評估結果（信心度）和配置的權重來選擇最佳解析器。
    3.  **信心度調整**: 驗證最終返回的 `ParsedQuery` 的信心度是否根據所選解析器的原始信心度和其配置權重進行了正確的調整。
    4.  **錯誤處理與健壯性**: 全面測試當任何一個子解析器在評估或執行過程中拋出異常時，`CompositeParser` 是否能捕獲異常、記錄失敗並優雅地回退，最終返回一個表示失敗的 `UNKNOWN` 類型的查詢，而不是讓整個系統崩潰。
    5.  **回退機制**: 測試在所有子解析器的信心度都低於預設閾值時，系統是否能正確地回退。
    6.  **配置管理**: 驗證對解析器權重、回退閾值等內部配置的設置和驗證邏輯。

*   **🧠 在系統架構中的定位（上層來源與下游依賴）：**
    *   **定位**: 位於測試層，專門驗證 NL-to-SQL 服務中的 `CompositeParser`。這是實現複雜、多層次解析策略的關鍵組件，是 NL-to-SQL 功能的大腦。
    *   **上層來源**: 由 `pytest` 測試框架驅動。
    *   **下游依賴**:
        *   `src.services.nl_to_sql.parsers.composite_parser.CompositeParser` (被測對象)
        *   `src.services.nl_to_sql.interfaces.parsing_interfaces.IParser` (作為子解析器的契約接口)
        *   `src.services.nl_to_sql.models.query_models.ParsedQuery` (作為解析結果的數據模型)
        *   `pytest`

*   **🔁 是否處理通訊 / 外部互動：**
    否。所有子解析器都被 `MockParser` 替代，不涉及任何真實的 I/O 或 AI API 調用。

*   **🎯 實用比喻：**
    此測試文件像是在考核一個大型醫院急診室的「分診主管」（`CompositeParser`）。考核內容是：
    1.  **團隊管理**: 驗證主管能否管理好他的醫生團隊（子解析器），包括讓新醫生入職（`add_parser`）和讓醫生離職（`remove_parser`）。
    2.  **分診策略**: 當一個病人（用戶輸入）進來時，主管會讓每個醫生快速評估一下病情（`can_handle`），然後根據醫生的專業判斷（信心度）和經驗資歷（權重），將病人分配給最合適的醫生（選擇最佳解析器）。
    3.  **風險評估**: 主管在記錄病例時，會結合醫生的判斷和資歷，給出一個綜合的診斷信心指數（調整後的信心度）。
    4.  **處理醫療事故**: 如果某個醫生在診斷時突然出錯（子解析器異常），主管必須能立即接管，確保病人安全，並記錄下這次失敗的嘗試，然後將病人轉為「待觀察」狀態（返回 `UNKNOWN` 查詢），而不是讓整個急診室陷入混亂。
    5.  **無法處理的病人**: 如果所有醫生都覺得病情棘手（信心度均低於閾值），主管會啟動應急預案（回退機制）。

### **【類別分析】**

*   **類別名稱：** `MockParser`
    *   **📌 創建目的：** 創建一個完全可控的 `IParser` 假實現。它允許測試精確地設置每個模擬解析器的名稱、信心度、返回類型，以及是否應該拋出異常。這是能夠對 `CompositeParser` 的複雜策略進行精確測試的關鍵。

*   **類別名稱：** `TestCompositeParser`
    *   **📌 創建目的：** 通過一系列嵌套的子類，從不同維度全面地測試 `CompositeParser`。
    *   **🧩 內含哪些關鍵測試類：**
        *   `TestInitialization`: 驗證初始狀態。
        *   `TestParserManagement`: 驗證添加/移除子解析器的邏輯。
        *   `TestParsingStrategy`: 測試核心的解析器選擇和信心度調整邏輯。
        *   `TestErrorHandling`: **極其關鍵**，覆蓋了各種子解析器失敗的場景，確保了組合器的健壯性。
        *   `TestCapabilityAssessment`: 專門測試 `can_handle` 這個聚合評估方法的邏輯。
        *   `TestConfigurationManagement`: 測試權重、閾值等配置的管理。
        *   `TestInformationRetrieval`: 測試獲取解析器信息和統計數據的功能。
        *   `TestParserSelection`: 更細緻地測試選擇最佳解析器的內部邏輯。

    *   **💡 設計考量：**
        *   **結構化測試**: 使用嵌套類來組織測試用例，使得測試的意圖非常清晰，每個子類專注於一個特定的功能領域。
        *   **策略與執行分離**: `CompositeParser` 的設計完美地體現了策略（選擇哪個解析器）與執行（實際解析）的分離。

### **【架構師補充面向】**

*   **🧩 設計模式**:
    *   **組合模式 (Composite Pattern)**: `CompositeParser` 自身實現了 `IParser` 接口（雖然在當前代碼中未顯式繼承，但行為上一致），並持有一組 `IParser` 對象。這使得上層調用者可以像對待單個解析器一樣對待這個組合體。
    *   **策略模式 (Strategy Pattern)**: `CompositeParser` 內部持有多個解析策略（子解析器），並在運行時根據情況選擇一個來執行。
*   **SOLID 原則**:
    *   **O (開閉原則)**: 系統對擴展開放，對修改關閉。當需要引入一種新的解析技術（例如，基於知識圖譜的解析器）時，只需實現一個新的 `IParser` 並將其添加到 `CompositeParser` 中，而無需修改 `CompositeParser` 的核心代碼。
    *   **D (依賴反轉)**: `CompositeParser` 依賴於 `IParser` 抽象接口，而不是任何具體的解析器實現。
