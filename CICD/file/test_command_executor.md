### **【文件角色摘要】**

*   **📌 主要功能與責任：**
    此文件是 `CommandExecutor` 的單元測試集。`CommandExecutor` 是領域層中負責解析和執行用戶指令的核心組件。此測試文件的核心職責是：
    1.  **初始化與註冊**: 驗證執行器能否正確初始化，並從指令註冊表 (`CommandRegistry`) 中註冊所有可用的指令處理器 (`CommandHandler`)。
    2.  **指令解析**: 測試執行器能否正確解析原始文本訊息，提取出指令名稱和參數。
    3.  **指令分發**: 驗證執行器在解析成功後，能否根據指令名稱找到對應的 `CommandHandler`。
    4.  **參數驗證**: 確保在執行指令前，會先調用對應處理器的 `validate_args` 方法進行參數驗證。
    5.  **執行委派**: 在驗證通過後，確保 `handle` 方法被以正確的參數（`user_id`, `args`）調用。
    6.  **錯誤與邊界場景處理**: 全面測試各種失敗路徑，包括指令解析失敗、參數驗證失敗、找不到處理器、處理器執行時拋出異常等，並驗證是否拋出了符合預期的自定義異常（`CommandParsingException`, `ValidationException`）。
    7.  **延遲初始化 (Lazy Initialization)**: 驗證執行器的初始化操作（註冊指令）是否在首次需要時才被觸發，而不是在實例化時就執行。

*   **🧠 在系統架構中的定位（上層來源與下游依賴）：**
    *   **定位**: 位於測試層，專門驗證領域層的 `CommandExecutor`。這是實現「指令模式」(Command Pattern) 的核心執行者。
    *   **上層來源**: 由 `pytest` 測試框架驅動。
    *   **下游依賴**:
        *   `src.domain.command_executor.CommandExecutor` (被測對象)
        *   `src.domain.command_handler.CommandHandler` (作為接口和模擬的基類)
        *   `get_command_registry` (被模擬的依賴，用於獲取註冊表)
        *   `CommandParsingException`, `ValidationException` (自定義異常)
        *   `pytest`, `unittest.mock`

*   **🔁 是否處理通訊 / 外部互動：**
    否。測試完全在領域層內部，所有 `CommandHandler` 的具體實現（可能涉及外部互動）都被模擬了。

*   **⚙️ 是否處理設定管理：**
    否。它接收一個模擬的 `CommandContext`，但自身不處理配置。

*   **🧪 是否負責資料驗證、格式轉換或協定解析：**
    是。它的核心職責之一就是解析原始字串，將其轉換為結構化的指令（名稱 + 參數列表）。同時，它委派參數的驗證工作給具體的 `CommandHandler`。

*   **💡 是否涉及平台相依性、跨平台兼容性、錯誤恢復：**
    *   **平台相依性**: 無。
    *   **錯誤恢復**: 是。透過拋出特定的業務異常，它為上層服務（如 `MessagingApplicationService`）提供了清晰的錯誤信號，使其能夠針對不同類型的失敗做出相應的處理。

*   **🎯 實用比喻：**
    此測試文件就像是對一個軍隊指揮官的模擬考核。考核內容是：
    1.  **戰前準備**: 驗證指揮官（`CommandExecutor`）在上任時（初始化），是否能熟悉他手下所有單位（`CommandHandler`）的職能（註冊指令）。
    2.  **命令解讀**: 當接到一封電報（原始文本訊息）時，驗證指揮官能否準確解讀出命令代號和具體參數（解析指令）。
    3.  **任務分配**: 驗證指揮官能否根據命令代號，準確地將任務分配給對應的作戰單位（分發給 `CommandHandler`）。
    4.  **可行性評估**: 在下達命令前，是否會先讓作戰單位評估命令的可行性（`validate_args`）。
    5.  **處理突發狀況**: 當遇到無法解讀的電報（解析失敗）、作戰單位報告無法執行（驗證失敗）或作戰單位失聯（找不到處理器）時，指揮官是否能按照預案流程處理（拋出特定異常）。

### **【類別分析】**

*   **類別名稱：** `MockCommandHandler`
    *   **📌 創建目的：** 創建一個簡單、可控的 `CommandHandler` 假實現，專門用於測試 `CommandExecutor`。它使得測試可以專注於執行器的分發和委派邏輯，而不用關心具體指令的複雜實現。

*   **類別名稱：** `TestCommandExecutor`
    *   **📌 創建目的：** 作為主測試套件，確保 `CommandExecutor` 在各種情況下的行為都符合預期。
    *   **🧩 內含哪些關鍵方法與邏輯功能：**
        *   `test_initialization_*`: 測試初始化邏輯。
        *   `test_initialize_once`: 確保初始化操作的冪等性。
        *   `test_register_all_commands`: 驗證指令註冊流程。
        *   `test_execute_command_success`: 測試理想的成功路徑。
        *   `test_execute_command_*_failure`: 覆蓋了多種關鍵的失敗場景，如解析失敗、驗證失敗。
        *   `test_execute_command_*_exception`: 測試更深層次的異常，如找不到處理器或處理器內部出錯。
        *   `*_auto_initialize`: 測試延遲初始化特性，確保在調用 `execute_command`, `has_command`, `list_commands` 等方法時，如果尚未初始化，會自動觸發。

    *   **💡 設計考量：**
        *   **職責分離**: 測試清晰地分離了對「執行器邏輯」和「具體指令邏輯」的關注。
        *   **健壯性**: 大量測試用例都集中在錯誤處理和邊界條件上，這表明對執行器的穩健性有很高的要求。
        *   **效能**: 延遲初始化 (`lazy initialization`) 是一個效能優化策略，避免在應用啟動時就執行可能耗時的指令註冊過程。測試文件對此特性進行了專門的驗證。

### **【架構師補充面向】**

*   **🧪 可測試性：** 非常高。`CommandExecutor` 的設計遵循了依賴反轉原則，它依賴於 `CommandHandler` 的抽象接口和 `CommandRegistry`，而不是具體的實現。這使得測試變得非常簡單，只需提供這些依賴的模擬版本即可。
*   **🧩 設計模式**: 該模組是「指令模式」和「註冊表模式」的一個經典實現。
    *   **指令模式**: 將請求（用戶輸入的文本）封裝成一個對象（雖然這裡沒有顯式的 Command 對象，但解析出的 `(name, args)` 起到了同樣作用），從而將請求的發送者和接收者解耦。
    *   **註冊表模式**: 使用 `CommandRegistry` 來集中管理和查找所有的指令處理器。
*   **♻️ 是否為共享模組（utility）或純服務模組（service）：** `CommandExecutor` 是一個純粹的領域服務，封裝了核心業務邏輯。
