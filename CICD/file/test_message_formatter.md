### **【文件角色摘要】**

*   **📌 主要功能與責任：**
    此文件是 `MessageFormatter` 服務的單元測試集。`MessageFormatter` 是一個領域服務，其核心職責是將結構化的內部數據（如資料庫查詢結果、錯誤信息）轉換為對終端用戶友好的、可讀的 `Linebot` 訊息格式（主要是 `TextMessage`）。此測試文件的主要職責是：
    1.  **驗證不同查詢結果的格式化**: 根據不同的查詢類型 (`QueryType`)，測試服務能否生成對應的、格式正確的文本訊息。這包括對機台狀態、生產統計、故障分析等多種業務場景的驗證。
    2.  **處理成功與失敗路徑**: 驗證服務能分別處理成功的查詢結果（有數據或無數據）和失敗的查詢結果（錯誤信息），並生成適當的用戶反饋。
    3.  **驗證輔助訊息格式化**: 測試如「建議訊息」(`format_suggestion_message`) 等非查詢結果類訊息的生成。
    4.  **檢查內部映射**: 驗證內部使用的數據到視圖的映射（如 `status_icons`, `department_icons`）是否正確加載和工作。
    5.  **處理邊界情況**: 測試當遇到未知的查詢類型時，服務是否能夠優雅地處理，而不是崩潰。

*   **🧠 在系統架構中的定位（上層來源與下游依賴）：**
    *   **定位**: 位於測試層，專門驗證領域層中的 `MessageFormatter` 服務。它處於應用程式的「表示層」(Presentation Layer) 的邊緣，是將內部狀態轉換為外部視圖的最後一環。
    *   **上層來源**: 由 `pytest` 測試框架驅動。
    *   **下游依賴**:
        *   `src.services.message_formatter.MessageFormatter` (被測對象)
        *   `src.services.nl_to_sql.models.query_models.QueryType` (作為輸入數據的一部分)
        *   `linebot.v3.messaging.TextMessage` (作為輸出的格式)
        *   `pytest`

*   **🔁 是否處理通訊 / 外部互動：**
    否。它只是一個純粹的數據轉換器，不執行任何 I/O 操作。

*   **⚙️ 是否處理設定管理：**
    否。

*   **🧪 是否負責資料驗證、格式轉換或協定解析：**
    是。它的全部職責就是**格式轉換**：`dict` -> `TextMessage`。

*   **🎯 實用比喻：**
    此測試文件就像是在審核一位專業的「新聞發言人」或「公關稿撰寫人」（`MessageFormatter`）。審核的重點是：
    1.  **素材處理能力**: 給定不同主題的原始數據（不同 `QueryType` 的結果），發言人能否撰寫出內容準確、格式得體的對外公告（`TextMessage`）。
    2.  **正面與負面新聞**: 無論是發布好消息（成功查詢）還是壞消息（錯誤結果），發言人都能用適當的口吻來傳達。
    3.  **圖文並茂**: 發言人懂得適時使用一些小圖標 (emojis) 來增強信息的可讀性（`status_icons`）。
    4.  **應對意外**: 即使給了發言人一份他從未見過的文件（未知查詢類型），他也能寫出一份通用的、不會出錯的公告，而不是啞口無言。

### **【類別分析】**

*   **類別名稱：** `TestMessageFormatter`
    *   **📌 創建目的：** 驗證 `MessageFormatter` 的所有公開方法的行為是否符合預期。
    *   **🧩 內含哪些關鍵方法與邏輯功能：**
        *   `test_formatter_initialization`: 確保格式化器在創建時，其內部的 icon 映射等靜態資源已準備就緒。
        *   `test_format_query_result_*`: 這是核心測試集，針對 `format_query_result` 這個主方法，輸入各種結構的 `result` 字典，斷言輸出是否為 `TextMessage` 且內容符合預期。
        *   `test_format_*_result`: 針對特定業務場景（如機台狀態、生產統計）的格式化進行更詳細的測試。
        *   `test_format_suggestion_message`: 驗證建議訊息的生成。
        *   `test_*_icon_mapping`: 直接測試內部 icon 映射字典的正確性。
        *   `test_format_unknown_query_type`: 測試對未知輸入的容錯能力。

    *   **💡 設計考量：**
        *   **數據驅動**: 測試主要是數據驅動的。通過構建不同的 `result` 字典來模擬各種場景，然後驗證輸出。
        *   **職責單一**: `MessageFormatter` 的職責非常單一（格式化），這也使得對它的測試非常直接和清晰。
        *   **鬆散斷言**: 值得注意的是，許多測試用例（如 `test_format_query_result_success`）中的斷言是 `assert len(message.text) > 0`，而不是檢查具體的文本內容。這是一種**權衡**：它給了開發者修改具體措辭的自由，而不會輕易破壞測試；但缺點是它沒有嚴格驗證格式化的精確細節。更詳細的測試（如 `test_format_machine_status_result`）通過檢查關鍵字 `assert "M001" in message.text` 來彌補這一點。

### **【架構師補充面向】**

*   **🧪 可測試性：** 極高。`MessageFormatter` 是一個純函數式的服務（無副作用，輸出僅依賴於輸入），這是最容易測試的代碼類型。
*   **🧩 設計模式**: 可以看作是 **Adapter** 或 **Facade** 模式的一種變體，它將系統內部的數據結構「適配」成 `linebot` 框架所期望的 `TextMessage` 格式。
*   **⚠️ 潛在風險與改進建議：**
    *   **硬編碼的文本**: 所有的返回文本（如 "建議"、"試試"）都硬編碼在 Python 代碼中。在需要支持多語言或需要由非開發人員修改返回話術的場景下，這種做法缺乏靈活性。可以考慮將這些文本模板提取到獨立的配置文件（如 YAML 或 JSON）或國際化 (i18n) 框架中。
    *   **複雜的格式化邏輯**: 隨著支持的 `QueryType` 增多，`format_query_result` 方法內部的 `if/elif/else` 結構可能會變得非常龐大和複雜。可以考慮使用更可擴展的設計，例如「策略模式」，為每種 `QueryType` 創建一個專門的格式化策略類，`MessageFormatter` 則根據 `QueryType` 委派給對應的策略對象。這將使代碼更符合開閉原則。
