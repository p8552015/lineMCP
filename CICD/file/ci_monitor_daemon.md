### **【文件角色摘要】**

*   **📌 主要功能與責任：**
    此文件是一個**獨立的守護進程 (Daemon)**，其核心職責是**持續監控指定的 GitHub Repository 的 CI/CD (GitHub Actions) 狀態**。主要功能包括：
    1.  **定期輪詢**: 按設定的間隔（預設5分鐘）主動向 GitHub API 查詢最新的 Workflow 執行狀態。
    2.  **狀態變更檢測**: 比較本次查詢與上次查詢的狀態，識別出 CI 狀態的變化（如從 `in_progress` 到 `success`）。
    3.  **失敗/恢復檢測**: 明確識別出從「成功/其他」轉為「失敗」的事件，以及從「失敗」轉為「成功」的恢復事件。
    4.  **事件驅動回調**: 提供一個回調機制 (`register_callbacks`)，允許外部邏輯在檢測到失敗、恢復或狀態變更時被觸發。
    5.  **日誌與報告**: 詳細記錄所有檢查活動、狀態變更和錯誤到日誌文件，並能在程式結束時生成一份監控總結報告。
    6.  **優雅關閉**: 能夠響應 `SIGINT` (Ctrl+C) 和 `SIGTERM` 信號，實現優雅地停止監控循環並保存最終報告。

*   **🧠 在系統架構中的定位（上層來源與下游依賴）：**
    *   **定位**: 這是一個**運維/自動化工具**，位於整個開發生命週期的監控層。它不屬於核心應用程式的一部分，而是一個輔助性的、用於提升開發與維運效率的工具。
    *   **上層來源**: 由作業系統的排程器（如 `cron`）或手動在終端中啟動。它是一個頂層的可執行腳本。
    *   **下游依賴**:
        *   `github_ci_validator.GitHubCIValidator` (核心依賴，用於與 GitHub API 互動)
        *   `asyncio`, `signal` (Python 標準庫，用於異步操作和信號處理)
        *   GitHub API (外部服務)

*   **🔁 是否處理通訊 / 外部互動：**
    是。這是它的核心功能。它透過 `GitHubCIValidator` 模組與 GitHub.com 的 REST API 進行通訊，以獲取 CI/CD 的狀態數據。

*   **⚙️ 是否處理設定管理：**
    是。它在初始化時接收必要的配置，如 GitHub Token、倉庫擁有者/名稱、檢查間隔和日誌文件路徑。其中，GitHub Token 是一個關鍵的秘密配置。

*   **🧪 是否負責資料驗證、格式轉換或協定解析：**
    是。它解析從 `GitHubCIValidator` 獲取的 API 回應，提取出如 `run_id`, `status`, `conclusion` 等關鍵資訊，並將其組裝成內部使用的 `report` 字典結構。

*   **💡 是否涉及平台相依性、跨平台兼容性、錯誤恢復：**
    *   **平台相依性**: 輕微。`signal` 模組在非 Unix-like 系統（如 Windows）上的行為可能不同，但對於主要的部署環境（Linux/macOS）來說是標準的。
    *   **錯誤恢復**: 是。主檢查循環 `check_ci_status` 中有一個頂層的 `try...except` 區塊，可以捕獲檢查過程中的任何異常（如網絡問題、API 錯誤），記錄錯誤後繼續下一次循環，確保了守護進程的健壯性。

*   **🔐 是否與授權、安全、敏感操作有關：**
    是。它需要一個 GitHub Personal Access Token (`token`) 來進行認證，這是一個敏感的憑證。

*   **🎯 實用比喻：**
    此守護進程就像一個不知疲倦的工廠品管員，他的工作台上有一個螢幕，實時顯示著自動化生產線（CI/CD Workflow）的狀態。他的工作是：
    1.  每隔五分鐘，就抬頭看一次螢幕（輪詢 API）。
    2.  如果螢幕顯示紅色警報（CI 失敗），他會立刻按下紅色按鈕（觸發 `on_failure_detected` 回調），並在自己的工作日誌上記上一筆。
    3.  如果螢幕從紅色變回綠色（CI 恢復），他會按下綠色按鈕（`on_recovery_detected`），並在日誌中標註問題已解決。
    4.  當下班鈴響起時（`SIGINT`/`SIGTERM`），他會整理好自己的工作日誌，寫一份當日總結（`save_monitoring_report`），然後才關燈下班（優雅關閉）。

### **【類別分析】**

*   **類別名稱：** `CIMonitorDaemon`
    *   **📌 創建目的：** 封裝 CI 監控的所有邏輯，提供一個易於啟動、配置和擴展的守護進程框架。
    *   **🧭 使用場景：** 在 CI/CD 伺服器或任何可以持續運行的環境中作為背景服務執行，以實現對開發流程的自動化監控。
    *   **📂 管理資源：** 管理日誌文件、運行狀態 (`self.running`)、內部統計數據 (`self.stats`) 以及與 GitHub API 的連接（透過 `validator`）。
    *   **🧩 內含哪些關鍵方法與邏輯功能：**
        *   `__init__`, `setup_logging`: 初始化和配置。
        *   `register_callbacks`: 核心擴展點，實現了策略模式，將「檢測」與「響應」解耦。
        *   `check_ci_status`: 主業務邏輯，包含 API 調用、狀態比較和事件分發。
        *   `_handle_*`: 針對不同事件（失敗、恢復、狀態變更）的私有處理方法。
        *   `start_monitoring`, `stop_monitoring`: 控制守護進程生命週期。
        *   `_signal_handler`: 實現優雅關閉的關鍵。
    *   **🔄 是否支援擴充或注入：** 是。回調機制是其核心的擴展方式，非常靈活。
    *   **⚙️ 是否耦合其他模組或設定來源：** 與 `GitHubCIValidator` 緊密耦合，這是合理的，因為它是其核心依賴。
    *   **💡 設計考量：**
        *   **SOLID**:
            *   **SRP**: 類別職責單一，專注於監控。
            *   **OCP**: 對擴展開放（透過回調），對修改關閉。當需要新的失敗響應時，只需註冊新回調，無需修改 `CIMonitorDaemon` 內部代碼。
        *   **健壯性**: 透過異步處理、信號處理和全面的異常捕獲，確保了長時間運行的穩定性。
    *   **✅ 是否容易測試 / 是否有測試機制設計：** 可測試性良好。雖然文件本身沒有測試，但其設計使得測試變得容易：可以模擬 `GitHubCIValidator` 來返回各種 CI 狀態，然後斷言對應的回調函數是否被以正確的參數調用。

### **【架構師補充面向】**

*   **🧠 能否重構為 microservice 或 reusable package：** 這本身就是一個可重用的工具。它可以被打包成一個獨立的 PyPI 包，任何項目都可以安裝和使用它來監控自己的 GitHub 倉庫，只需提供配置即可。
*   **⚠️ 潛在風險與改進建議：**
    *   **API 速率限制**: 目前的實現沒有明確處理 GitHub API 的速率限制 (Rate Limiting)。如果檢查間隔設置得太短或監控多個倉庫，可能會耗盡 API 限額。可以考慮在 `GitHubCIValidator` 層面增加速率限制的檢測和等待邏輯。
    *   **狀態持久化**: 守護進程重啟後，`last_run_status` 和 `failure_count` 等內存中的狀態會丟失，這可能導致重啟後立即產生錯誤的「恢復」或「失敗」事件。可以考慮將這些狀態定期持久化到一個簡單的 state 文件 (如 JSON 或 atexit) 中。
    *   **配置管理**: Token 等敏感信息目前是作為參數傳入，在實際部署時，應考慮使用更安全的方式，如環境變數或專門的秘密管理工具。
