# 檔案分析報告：`apps/bot/src/services/nl_to_sql/models/query_models.py`

## 1. 檔案目的與角色

此檔案是 NL-to-SQL 新 SOLID 架構的**核心資料模型定義中心**。它不包含複雜的業務流程，其唯一且關鍵的職責是定義在系統各個元件（解析器、建構器、服務等）之間流動的、標準化的**資料傳輸物件 (DTOs)**。

它在架構中的核心角色是：
1.  **定義通用語言**: `ParsedQuery` 和 `QueryType` 構成了整個 NL-to-SQL 功能變數中所有元件溝通的「通用語言」。這確保了資訊在傳遞過程中的一致性和準確性。
2.  **確保型別安全**: 透過使用 Python 的 `Enum` 和 `dataclass`，並結合型別提示，極大地增強了程式碼的健壯性，減少了因資料類型錯誤引發的執行時 bug。
3.  **封裝資料與其內在邏輯**: `ParsedQuery` 不僅僅是一個被動的資料容器，它還封裝了與其自身狀態相關的簡單驗證和判斷邏輯，體現了良好的物件導向設計。

這個檔案是連接所有介面和服務的資訊載體，是系統中流動的「血液」。

## 2. 主要類別/函數定義

### `class QueryType(Enum)`
*   **職責**: 這是一個枚舉類別，用於**分類和抽象化**所有系統能夠理解的業務查詢意圖。
*   **成員**:
    *   `MACHINE_STATUS`, `FAULT_ANALYSIS`, `PRODUCTION_STATS` 等成員代表了具體的業務查詢場景。
    *   `UNKNOWN` 成員提供了一個標準化的失敗或未識別狀態，使錯誤處理更加清晰。
*   **重要性**: 將查詢意圖強型別化，避免了在程式碼中使用容易出錯的「魔術字串」，提高了可讀性和可維護性。

### `class ParsedQuery(dataclass)`
*   **職責**: 這是一個資料類別，作為從自然語言解析出的**結構化結果**的標準容器。它是 `IParser` 的輸出，也是 `IQueryBuilder` 的輸入。
*   **核心屬性**:
    *   `query_type: QueryType`: 標識解析出的查詢意圖。
    *   `sql_query: str`: AI 模型直接生成的 SQL，可能為空。
    *   `parameters: dict[str, Any]`: 從文字中提取出的關鍵參數，是後續建構 SQL 的依據。
    *   `confidence: float`: 解析結果的可信度評分。
    *   `explanation: str`: 對解析結果的文字說明，可用於除錯或向使用者展示。
*   **核心方法**:
    *   `__post_init__()`: 在物件創建後自動執行資料驗證，確保其內部狀態的有效性（如 `confidence` 值的範圍）。
    *   `is_successful()`: 一個便利的布林方法，用於快速判斷此次解析是否成功且可信。
    *   `has_sql_query()`: 快速檢查是否已包含由 AI 生成的 SQL。
    *   `to_dict()`: 將物件實例序列化為字典，方便日誌記錄或 API 傳輸。

## 3. 功能實現的簡要描述

這個檔案的功能是**定義資料結構**，而非執行流程。它定義了：
1.  一個 `QueryType` 枚舉，列出了所有已知的、系統可以處理的查詢類型。
2.  一個 `ParsedQuery` 資料類別，它像一個標準化的表格，包含了從使用者輸入中解析出的所有必要資訊欄位：意圖是什麼 (`query_type`)，信心有多高 (`confidence`)，提取出了哪些關鍵參數 (`parameters`)，以及 AI 可能給出的初步 SQL (`sql_query`) 和解釋 (`explanation`)。

任何 `IParser` 的實作，其目標就是產生一個填充好的 `ParsedQuery` 物件。任何 `IQueryBuilder` 的實作，其任務就是消費這個物件來工作。

## 4. 依賴關係

*   **`dataclasses.dataclass`**: 依賴 Python 標準庫的 `dataclass` 來快速、優雅地創建資料類別。
*   **`enum.Enum`**: 依賴 Python 標準庫的 `Enum` 來創建強型別的枚舉。
*   **`typing.Any`**: 用於型別提示。

這個檔案沒有任何外部依賴或對專案內其他模組的複雜依賴，體現了其作為**穩定基礎模型**的特性。

## 5. 設計模式與架構決策

*   **資料傳輸物件 (Data Transfer Object, DTO)**: `ParsedQuery` 是 DTO 模式的經典實現。它的主要目的是在不同層或服務之間傳輸資料，減少方法呼叫的次數，並將資料打包成一個標準化的結構。
*   **枚舉優於魔術字串 (Enums over Magic Strings)**: 使用 `QueryType` 是一個明確的、旨在提高程式碼品質的設計決策。
*   **防禦性程式設計**: 在 `__post_init__` 中加入驗證邏輯，是一種主動的防禦措施，確保不會在系統中流動著狀態無效的資料物件。
*   **資訊載體 (Information Carrier)**: 將所有相關資訊（意圖、參數、信心度、SQL、解釋）打包在一個物件中，而不是透過多個零散的變數傳遞，使得介面更簡潔，程式碼更易於理解和維護。

## 6. 潛在的改進點

*   **參數的強型別**: `parameters` 欄位目前是 `dict[str, Any]`。在更複雜的系統中，可以為每種 `QueryType` 定義一個對應的、更具體的參數資料類別（例如 `MachineStatusParameters(dataclass)`），然後讓 `parameters` 欄位的型別為這些類別的聯合（`Union`）。這會提供更強的型別安全性，但也會增加模型的複雜度。對於當前階段，`dict` 是一個務實且靈活的選擇。
*   **巢狀結構**: 目前模型是扁平的。如果未來查詢變得更複雜（例如，包含子查詢），`ParsedQuery` 可能需要支援巢狀結構。但對於目前定義的 `QueryType` 來說，扁平結構是完全足夠的。
