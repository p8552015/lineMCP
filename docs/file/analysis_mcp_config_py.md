## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案是**應用程式的配置中心**，統一管理所有與 MCP (Model-View-Controller a la Protocol) 相關的設定。
  - **核心職責**：
    1.  **定義強型別的配置結構**: 使用 Python 的 `dataclass` 定義了 `MCPServerConfig`, `MCPClientConfig`, 和 `NLToSQLConfig`，為不同模組的設定提供了清晰、自我說明的資料結構。
    2.  **分層的配置載入**: `MCPConfigManager` 類別實現了一個分層的配置載入策略。配置的優先級順序為：**環境變數 > YAML 檔案 > 程式碼中的預設值**。這使得配置在不同環境（開發、測試、生產）中可以被靈活地覆寫。
    3.  **提供全域訪問點**: 透過 `get_mcp_config()` 這個單例 (Singleton) 模式的工廠函式，應用程式的任何部分都可以方便地獲取到統一的配置管理器實例。

- 🧠 **在系統架構中的定位**:
  - **定位**：這是一個**基礎設施層的核心元件**。它不包含任何業務邏輯，但為所有業務邏輯模組提供它們所需要的運行參數。它解耦了「配置的定義與載入」和「配置的使用」。
  - **上層來源**：通常在應用程式啟動時（如 `main.py` 或服務工廠 `enhanced_service_factory.py`）被初始化。
  - **下游依賴**：應用程式中幾乎所有需要與外部服務（如 MCP Server、AI 服務）互動的模組，都會依賴這個配置管理器來獲取連線資訊、超時時間、重試次數等參數。

- 🎯 **實用比喻**:
  - `MCPConfigManager` 就像是一座大樓的**中央控制室**。控制室的儀表板（`dataclasses`）清晰地定義了所有可以調整的參數（空調溫度、電梯速度、照明亮度）。大樓管理員可以透過多種方式設定這些參數：可以直接在控制室的面板上手動設定（程式碼預設值），也可以透過外部的建築管理系統下發指令（環境變數）。而大樓中的每個設備（應用程式的各個服務）都連接到這個中央控制室，從中獲取自己的運行參數，而無需關心這些參數最初是如何被設定的。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`MCPConfigManager`
  - 📌 **創建目的**: 作為配置管理的**主要協調器**。它封裝了所有配置載入、覆寫、驗證和訪問的複雜邏輯，為外部呼叫者提供一個乾淨、簡單的介面。
  - 🧩 **內含哪些關鍵方法與邏輯功能**:
    - `__init__` & `_init_*()`: 初始化方法中包含了對不同配置模組（如 `_init_default_servers`, `_init_nl_to_sql_config`）的初始化呼叫，結構清晰。
    - `_load_*()` & `_apply_*()`: 完美地展示了**關注點分離**。`_load_*` 方法只負責從特定來源（環境變數、YAML）讀取原始資料，而 `_apply_*` 方法則負責將這些讀取到的資料應用到強型別的 `dataclass` 實例上。
    - `get_*()` & `update_*()`: 提供了一組標準的 Getter/Setter 介面，用於安全地訪問和動態修改配置。
    - `validate_server_config()`: 提供了一個內建的驗證機制，增加了系統的健壯性。
- 類別名稱：`MCPServerConfig`, `MCPClientConfig`, `NLToSQLConfig` (Dataclasses)
  - 📌 **創建目的**: 作為**強型別的資料容器**。
  - 💡 **設計考量**:
    - **強型別**: 使用 `dataclass` 替代了傳統的字典 (`dict`)。這帶來了巨大的好處：
        1.  **程式碼可讀性**：`config.nl_to_sql.cache_ttl` 遠比 `config['nl_to_sql']['cache_ttl']` 更易讀。
        2.  **開發期安全**: IDE 和靜態分析工具可以進行自動補全和型別檢查，減少了因為拼寫錯誤 (`'cahce_ttl'`) 而導致的執行期錯誤。
        3.  **預設值**: 可以方便地為每個欄位定義預設值。

## 🧩 樣板 4：模組關係與相依

- **上游呼叫者**：應用程式初始化程式碼、服務工廠。
- **下游相依元件**：任何需要配置參數的服務或模組。
- **是否存在循環相依**：**否**。作為一個基礎設施元件，它處於依賴鏈的底層，不應該依賴任何上層的業務邏輯模組。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。它被設計為一個低耦合的模組。
- 🧪 **可測試性**：**高**。
    - 可以輕易地在測試中創建一個 `MCPConfigManager` 的獨立實例。
    - 可以透過在測試環境中設定環境變數，來驗證 `_load_nl_to_sql_env_config` 的邏輯是否正確。
    - 可以傳入一個 Mock 的 `settings` 物件來測試與 YAML 檔案的互動。
- 🧠 **重構潛力**:
  - **配置來源抽象**: `_load_nl_to_sql_env_config` 和 `_load_nl_to_sql_yaml_config` 的邏輯是特定的。一個更進階的設計是定義一個 `IConfigSource` 介面，然後分別實現 `EnvironmentConfigSource` 和 `YamlConfigSource`。這樣，配置管理器就可以接受一個 `IConfigSource` 的列表，並按順序應用它們。未來如果需要新增從資料庫或遠端配置中心（如 Consul）載入配置，只需新增一個實現了 `IConfigSource` 介面的類別即可，無需修改 `MCPConfigManager` 本身。
  - **密文管理**: `MCPServerConfig` 中的 `api_key` 和資料庫連接字串目前是明文儲存的。在生產環境中，這是一個安全風險。應考慮與一個密文管理系統（如 HashiCorp Vault, AWS Secrets Manager）整合，在執行期動態地獲取這些敏感資訊，而不是將它們硬編碼或儲存在環境變數中。
