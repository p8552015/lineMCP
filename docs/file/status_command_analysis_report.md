## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - **實現 `/status` 指令**。其核心職責是**即時地**、**主動地**檢查系統中各個關鍵組件的健康狀況，並生成一份彙總的狀態報告。
    - **作為一個端到端的健康探針**。它不僅僅是報告服務是否已初始化，而是透過執行一個真實的操作（如 `_check_mcp_connection` 中的 `SELECT 1`）來驗證整個鏈路是否通暢。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：**指令模式**中的一個具體**指令處理器 (Concrete Command Handler)**，是一個高層次的診斷工具。
    - **上層來源**：被 `domain.CommandExecutor` 呼叫。
    - **下游依賴**：
        1.  `domain.CommandContext`: 強烈依賴指令上下文，因為它需要從中獲取所有需要被檢查的服務實例，如 `mcp_client`, `ai_model_service`, `db_service` 等。

- 🔁 **是否處理通訊 / 外部互動**：
    - **是**。`_check_mcp_connection` 方法會實際發起一個到 `sqlite` 工具的查詢請求，這是一個真實的跨進程通訊，用以驗證連接的活性。

- ⚙️ **是否處理設定管理**：
    - **否**。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **是**。它的核心功能就是將從各個服務檢查中得到的、零散的狀態資訊（`healthy`, `warning`, `error`）**轉換並格式化**（`_format_status_report`）成一份帶有狀態圖示（✅⚠️❌）、對用戶友善的、結構化的報告。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是，而且設計得非常穩健**。
        1.  **主流程錯誤恢復**：`handle` 方法本身被 `try...except` 包圍，防止整個指令因意外失敗而崩潰。
        2.  **組件級錯誤恢復**：**更重要的是**，每一個獨立的檢查方法（如 `_check_mcp_connection`, `_check_ai_service`）都有自己的 `try...except` 區塊。這確保了**單一組件的檢查失敗不會影響到其他組件的檢查**。例如，即使 AI 服務崩潰了，MCP 連接的狀態檢查依然可以成功執行並回報，使得這份狀態報告極具韌性。

- 🎯 **實用比喻**：
    - 它就像是**飛機起飛前的駕駛艙檢查清單**。飛行員（用戶）按下「開始檢查」按鈕 (`/status`)，系統會自動檢查引擎（MCP 連接）、導航系統（AI 服務）、燃油系統（資料庫服務）等。每個系統都會回報「正常」、「注意」或「故障」。最後，一份完整的檢查報告會顯示在主螢幕上，並給出一個總結：「所有系統正常，可以起飛」或「引擎需要注意，建議檢修」。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`StatusCommandHandler`
- 📌 **創建目的**：
    - 將系統健康狀況的檢查邏輯**集中化**，提供一個單一的入口來了解整個系統的健康全貌。
- 🧭 **使用場景**：由 `CommandExecutor` 呼叫。
- 📂 **管理資源**：不管理任何外部資源。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `handle()`: 協調整個檢查和報告流程。
    - `_perform_status_checks()`: 負責**呼叫**所有獨立的檢查方法，並**聚合**它們的結果。
    - `_check_*()` 系列方法: 每個方法都是一個獨立的、專注於檢查單一服務或組件的**檢查單元**。
    - `_format_status_report()`: **表現層**。將聚合後的檢查結果數據轉換為最終的文字報告。
- 💡 **設計考量**：
    - **模組化與可擴充性**：設計得非常容易擴充。要新增一個對新服務的檢查，只需要：1) 增加一個新的 `_check_new_service()` 方法；2) 在 `_perform_status_checks` 中呼叫它；3) 在 `_format_status_report` 中添加對其結果的顯示。原有代碼幾乎不受影響。
    - **韌性 (Resilience)**：如前所述，組件級的錯誤處理是其設計上的一大優點。
