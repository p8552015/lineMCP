## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `TablesCommandHandler` 類別，是一個具體的指令處理器，專門負責處理 `/tables` 指令。
  - **核心職責**：提供了兩種不同的資料庫元數據查詢功能：
    1.  **列出所有資料表 (`/tables`)**: 當指令不帶任何參數時，它會查詢 `information_schema.tables` 來獲取資料庫中所有公開的資料表列表。
    2.  **查詢特定資料表結構 (`/tables <table_name>`)**: 當指令帶有一個參數（資料表名稱）時，它會查詢 `information_schema.columns` 來獲取指定資料表的詳細欄位結構（欄位名、類型、是否可為空等），並額外執行一條 `COUNT(*)` 語句來獲取該表的總行數。
  - 它與 `/sql` 指令一樣，都直接與後端的 MCP `postgres` 工具互動來執行 SQL 查詢。

- 🧠 **在系統架構中的定位**:
  - **定位**：在 `commands` 模組中，它是一個**資料庫探索工具**的具體實現。它為使用者提供了一個無需編寫 SQL 就能查看資料庫基本結構的便捷方式。
  - **上層來源**：由 `CommandExecutor` 在解析到 `/tables` 指令時調用。
  - **下游依賴**：`CommandContext` (用於獲取 MCP 客戶端)。

- 🎯 **實用比喻**:
  - `TablesCommandHandler` 就像是圖書館的**索引卡片目錄**。如果你不知道圖書館裡有哪些書（`/tables`），你可以查閱這個目錄來看到所有書名。如果你對某一本書感興趣（`/tables <book_name>`），你可以抽出這本書的索引卡片，上面詳細記錄了書的作者、出版社、章節列表等資訊（資料表結構）。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`TablesCommandHandler`
- 📌 **創建目的**:
  - **核心目的**：降低使用者探索資料庫結構的門檻。使用者無需記住或編寫查詢 `information_schema` 的複雜 SQL，只需使用簡單的指令即可。
  - **具體目的**：作為 `/sql` 指令的一個重要輔助工具，讓使用者可以先透過 `/tables` 了解有什麼表、表裡有什麼欄位，然後再用 `/sql` 構建精確的查詢。
- 🧭 **使用場景**:
  - 使用者想知道資料庫裡有哪些可供查詢的資料時。
  - 使用者在編寫複雜的 `/sql` 查詢前，想確認某個表的結構時。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `handle()`: 作為一個**分發器 (Dispatcher)**，根據參數 `args` 是否存在，將請求分發給 `_list_all_tables` 或 `_get_table_schema` 兩個不同的私有方法處理。
  - `_list_all_tables()`: 實現列出所有資料表的邏輯。
  - `_get_table_schema()`: 實現獲取特定資料表結構的邏輯。這個方法中執行了**兩次**資料庫查詢（一次查結構，一次查行數）。
  - 這兩個方法都包含了呼叫 MCP 客戶端、解析結果和格式化輸出訊息的完整流程。
- 💡 **設計考量**:
  - **單一職責**: 該類別的職責非常清晰，就是處理 `/tables` 指令。
  - **使用者體驗**: 在 `handle` 方法中對有無參數的情況進行了不同的處理，提供了更豐富的功能。返回的訊息格式也經過精心設計，包含了後續操作的提示（如 "💡 查看資料表結構：..."），引導使用者進行下一步操作。
  - **內部實現**: 將兩種不同的功能邏輯拆分到 `_list_all_tables` 和 `_get_table_schema` 兩個獨立的私有方法中，使得 `handle` 方法本身保持簡潔，可讀性更高。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。
- 🧪 **可測試性**：**高**。與 `SqlCommandHandler` 類似，可以輕易地 Mock `CommandContext` 和 `MCPResponseParser` 來進行單元測試。可以分別測試無參數和有參數兩種情況下的邏輯是否正確。
- 🧠 **重構潛力**:
  - **SQL 注入風險**: 在 `_get_table_schema` 方法中，`table_name` 是直接透過 f-string 拼接到 SQL 語句中的。儘管資料表名稱通常不會包含惡意字元，但這依然是一個潛在的 SQL 注入風險點。最佳實踐是，在使用 `table_name` 之前，對其進行嚴格的白名單驗證，或者使用資料庫驅動提供的安全方式來引用識別碼（Identifier）。
  - **效能優化**: `_get_table_schema` 方法執行了兩次獨立的查詢。在某些情況下，可以考慮將這兩次查詢合併或優化。但考慮到這是個人工觸發的低頻操作，目前的實現是完全可以接受的。
  - **程式碼複用**: `_list_all_tables` 和 `_get_table_schema` 中都有重複的「獲取 MCP 客戶端 -> 呼叫 -> 解析」的程式碼塊。可以考慮將這段邏輯抽取到一個共享的輔助函式或一個 `BaseDbCommandHandler` 基底類別中，以減少重複程式碼。
