## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - **實現 `/info` 指令**。其核心職責是**收集**並**格式化**關於應用程式本身及其運行環境的各種資訊，例如應用版本、Python 版本、作業系統、可用功能和 AI 模型狀態。
    - **提供一個快速的系統診斷入口**。用戶或管理員可以透過此指令快速了解系統的配置和當前狀態。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：**指令模式**中的一個具體**指令處理器 (Concrete Command Handler)**。
    - **上層來源**：被 `domain.CommandExecutor` 在用戶輸入 `/info` 或其別名時呼叫。
    - **下游依賴**：
        1.  `domain.CommandContext`: 依賴指令上下文來獲取對其他服務的存取權，特別是 `ai_model_service`。
        2.  Python 標準函式庫: 如 `platform`, `sys`, `os`，用來獲取底層環境資訊。

- 🔁 **是否處理通訊 / 外部互動**：
    - **否**。它不與任何外部服務進行網路通訊，只查詢內部狀態和環境變數。

- ⚙️ **是否處理設定管理**：
    - **否**。但它會讀取環境變數 (`os.getenv("ENVIRONMENT", ...`) 來判斷當前是生產環境還是開發環境。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **是**。它的核心功能之一就是將從各處收集來的原始、分散的資訊（`_collect_system_info`）**轉換並格式化**（`_format_system_info`）成一個對用戶友善、結構清晰的文字訊息。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是**。`handle` 和 `_get_ai_models_info` 方法中都包含了 `try...except` 區塊，確保在收集任何資訊（特別是可能失敗的 AI 服務資訊）時如果發生錯誤，指令不會崩潰，而是會回傳一個友善的錯誤訊息。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **否**。它只顯示公開的系統資訊。

- 🎯 **實用比喻**：
    - 它就像是**電腦上的「關於本機」或「系統內容」視窗**。它不會執行任何操作，但會提供一個關於硬體、作業系統、已安裝軟體和版本的完整快照，方便用戶或技術支援人員快速了解系統的全貌。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`InfoCommandHandler`
- 📌 **創建目的**：
    - 專門封裝和處理與 `/info` 指令相關的所有邏輯，將其與其他業務指令完全解耦。
- 🧭 **使用場景**：由 `CommandExecutor` 在應用啟動時註冊，並在用戶呼叫指令時執行。
- 📂 **管理資源**：不管理任何外部資源。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `handle()`: 指令的入口點和總協調器。
    - `_collect_system_info()`: **數據收集層**。負責從多個來源（Python 環境、注入的服務、硬編碼列表）拉取所有需要的資訊，並將它們組織到一個字典中。
    - `_format_system_info()`: **表現層**。負責將 `_collect_system_info` 產生的結構化數據轉換為用戶最終看到的、格式優美的文字訊息。
- 🔄 **是否支援擴充或注入**：
    - **是**。透過 `CommandContext` 注入，未來可以輕鬆地從更多注入的服務中收集資訊，而無需大幅修改代碼。
- 💡 **設計考量**：
    - **SRP (單一職責原則)**：職責非常清晰，只關心資訊的收集與展示。
    - **關注點分離 (Separation of Concerns)**：將**數據收集** (`_collect_system_info`) 和**數據展示** (`_format_system_info`) 分離到不同的方法中，這是一個非常好的實踐，使得邏輯更清晰，未來也更容易修改其中任一部分。
