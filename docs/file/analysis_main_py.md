## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案是整個 `apps/bot` 服務的**應用程式進入點 (Application Entry Point)**。
  - **核心職責**：初始化 FastAPI 應用實例、設定應用程式生命週期事件（啟動與關閉）、掛載中介軟體 (Middleware)、註冊 API 路由器 (Router)、並定義全域的健康檢查 (`/health`)、監控指標 (`/metrics`) 和例外處理機制。

- 🧠 **在系統架構中的定位**:
  - **定位**：位於應用程式的最頂層，是**服務的啟動與協調中心**。
  - **上層來源**：由 ASGI 伺服器（如 Uvicorn, Hypercorn）載入並執行 `app` 物件。
  - **下游依賴**：它整合了專案中各個關鍵模組，包括路由 (`routes`)、設定 (`config`)、中介軟體 (`middleware`) 及各式工具 (`utils`)。

- 🔁 **是否處理通訊 / 外部互動**:
  - **是**，但層次較高。它直接定義了 `/health` 和 `/metrics` 兩個基礎設施端點的 HTTP 處理邏輯。主要的業務邏輯通訊（如 `/webhook`）則透過 `app.include_router` 委派給 `src.routes.webhook` 模組處理。

- ⚙️ **是否處理設定管理**:
  - **是**。透過呼叫 `src.config.get_settings()` 載入應用程式所需的全域設定，並將其應用於 FastAPI 實例（如 `debug` 模式）。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**:
  - **否**。此檔案不直接處理業務資料的驗證或轉換。這些責任被委派給 Pydantic 模型和路由層的依賴注入。它僅定義了基礎設施端點（如健康檢查）的回應格式。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**:
  - **平台相依性**: 依賴 FastAPI 框架和 ASGI 伺服器標準。
  - **跨平台兼容性**: 非常高。作為一個標準的 Python Web 應用，可以輕易在任何支援 Python 的平台上運行，尤其是透過 Docker。
  - **錯誤恢復**:
    - 透過 `@app.exception_handler(Exception)` 定義了**全域例外處理器**，作為最後一道防線，捕獲所有未處理的例外，防止服務崩潰並回傳標準的 500 錯誤。
    - `lifespan` 管理器中的 `try...except` 區塊確保了在啟動過程中（如資料庫連線失敗），應用程式能夠優雅地失敗並記錄錯誤，而不是進入不健康的狀態。

- 🎯 **實用比喻**:
  - `main.py` 就像一個**建築的總設計圖與總承包商**。它定義了建築（FastAPI 應用）的主要結構，連接了水電系統（中介軟體、監控），設定了消防安全規章（全域例外處理），並在開業前進行了全面的安全檢查（`lifespan` 中的健康檢查），最後才正式對外開放（啟動伺服器）。

## 🧩 樣板 3：所有方法分析、使用情況與價值評估

【模組層級函式】

| 函式名稱 | 功能用途 | 使用情境 | 是否必要 | 替代方式 | 存在價值 |
|---|---|---|---|---|---|
| `lifespan` | 管理應用程式的啟動與關閉事件。 | 在 FastAPI 應用實例化時作為 `lifespan` 參數傳入。 | **是，關鍵** | 在每個路由中單獨處理連線（不推薦）。 | **極高**。集中管理啟動前的健康檢查（資料庫、Redis）和關閉時的資源釋放，是建立強固服務的標準實踐。 |
| `health_check` | 提供 HTTP `/health` 端點。 | 由容器編排系統（如 Kubernetes）或監控系統定期呼叫。 | **是，關鍵** | 無 | **極高**。為自動化的服務健康監控和自我修復提供了基礎。 |
| `global_exception_handler` | 捕獲所有未被處理的例外。 | 當應用程式任何地方拋出未捕獲的例外時觸發。 | **是，關鍵** | 無（或在 Middleware 中實現，但 Handler 更標準） | **極高**。防止敏感錯誤資訊（如堆疊追蹤）洩漏給客戶端，並提供統一的錯誤回報格式與追蹤 ID。 |

【補充分析】
- 🔄 **是否支援 retry / fallback / timeout**：此檔案本身不支援，但 `lifespan` 中的啟動檢查若失敗會直接阻止應用啟動，這是一種快速失敗 (Fail-Fast) 策略，比重試更適合此場景。
- 🔁 **是否非同步 async**：**是**。所有函式都定義為 `async def`，完全擁抱 Python 的非同步模型，以實現高效能 I/O。
- 📊 **測試覆蓋情況**：此檔案的邏輯相對簡單且關鍵，應有接近 100% 的測試覆蓋率（特別是透過 `TestClient` 測試端點和例外處理）。

## 🧩 樣板 4：模組關係與相依

- **上游呼叫者**：
  - **ASGI Server** (Uvicorn / Hypercorn): 載入並運行 `app` 物件。
- **下游相依元件**：
  - **FastAPI**: 核心 Web 框架。
  - **Observability Stack**: `structlog`, `opentelemetry`, `prometheus_client`。
  - **`src.config`**: 載入應用程式設定。
  - **`src.middleware`**: 設定中介軟體。
  - **`src.routes.webhook`**: 核心業務邏輯的路由器。
  - **`src.utils.*`**: 各種工具函式，如 Redis 客戶端、資料庫健康檢查等。
- **是否存在循環相依**：**否**。此檔案作為 Composition Root，只向下依賴，沒有模組反過來依賴它，結構清晰。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。此檔案的職責非常單一，就是「組合」與「設定」。它將所有業務邏輯都委派給其他模組，自身與業務邏輯解耦。
- ☁️ **容器化部署友善**：**極高**。`lifespan` 管理的啟動前健康檢查、`/health` 端點、`/metrics` 端點的設計，完全是為雲原生和容器化部署量身打造的最佳實踐。
- 🧪 **可測試性**：**高**。由於職責分離清晰，可以使用 FastAPI 的 `TestClient` 輕鬆地對此檔案定義的端點和行為進行整合測試，而其依賴的工具函式也可被輕易地 Mock。
- ♻️ **共享模組或純服務模組**：此檔案屬於**應用程式進入點 (Entry Point) / 組合根 (Composition Root)** 類型，其本身不可複用，但它組合了許多可複用的模組。
