## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - 為 FastAPI 應用程式**集中設定和註冊**所有 HTTP 中介軟體 (Middleware)。
    - 實現一系列**橫切關注點**，包括日誌記錄 (Logging)、指標監控 (Metrics)、追蹤 ID (Trace ID) 的生成與傳遞，以及安全性設定（如 CORS 和 Trusted Host）。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：處於**請求處理鏈的最前端**。所有傳入的 HTTP 請求在到達真正的路由處理函式之前，都會依序經過這個檔案中定義的中介軟體。
    - **上層來源**：由 `main.py` 在應用程式啟動時呼叫 `setup_middleware(app)` 來載入。
    - **下游依賴**：依賴 `FastAPI` 框架本身、`structlog` 用於日誌，以及 `prometheus_client` 用於監控指標。

- 🔁 **是否處理通訊 / 外部互動**：
    - **否**。它只在請求的生命週期內運作，不直接與外部服務通訊。

- ⚙️ **是否處理設定管理**：
    - **否**。但其設定（如 `allowed_hosts`）是硬編碼的 (`"*"`)，這在生產環境中可能需要改為從設定檔讀取。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **否**。它不關心請求的 body 或回傳的資料內容，只關心請求和回應的元資料（如 headers, status code）。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **否**。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **是**。它設定了 `CORSMiddleware` 和 `TrustedHostMiddleware`，這兩者是 Web 應用程式的基礎安全措施。

- 🎯 **實用比喻**：
    - 它就像是**機場的安檢和地勤人員**。每位旅客（HTTP 請求）在登機（到達路由處理器）之前，都必須經過一系列標準化流程：
        1.  **地勤蓋章 (`add_trace_id`)**: 給旅客的登機證蓋上一個獨一無二的追蹤號碼。
        2.  **安檢 (`CORS`, `TrustedHost`)**: 檢查旅客的來源是否合法。
        3.  **地勤記錄 (`logging_middleware`)**: 記錄旅客的進出時間。
        4.  **機場統計 (`prometheus_middleware`)**: 更新機場的即時人流、平均通關時間等統計數據。

## 🧩 樣板 3：所有方法分析、使用情況與價值評估

【方法總覽】
此處的方法均為在 `setup_middleware` 內部定義的中介軟體函式。

| 方法名稱 | 功能簡述 | 是否為關鍵邏輯 | 內部使用次數 | 外部被呼叫 | 錯誤處理 | 資源釋放 | 存在價值 |
|:---|:---|:---:|:---:|:---|:---:|:---:|:---:|
| `add_trace_id` | 為每個請求生成或傳遞追蹤ID | ✅ | 0 | FastAPI框架 | 否 | 否 | 極高 |
| `prometheus_middleware` | 收集並更新 Prometheus 指標 | ✅ | 0 | FastAPI框架 | ✅ | 否 | 極高 |
| `logging_middleware` | 記錄請求的開始、結束和耗時 | ✅ | 0 | FastAPI框架 | 否 | 否 | 極高 |

【模組層級函式】

| 函式名稱 | 功能用途 | 使用情境 | 是否必要 | 替代方式 | 存在價值 |
|:---|:---|:---|:---:|:---|:---:|
| `setup_middleware` | 將所有中介軟體註冊到 FastAPI 應用實例 | 啟動設定 | ✅ | 直接在 `main.py` 中逐一註冊 | 極高 |

【補充分析】
- **職責分離**: 將所有中介軟體的設定邏輯從 `main.py` 中抽離出來，放到 `setup_middleware` 這個單一函式中，使得 `main.py` 更乾淨，也讓中介軟體的管理更加集中，這是非常好的實踐。
- **執行順序**: 在 FastAPI 中，中介軟體的執行順序與它們被**註冊的順序相反**。因此，實際的執行順序是 `logging_middleware` -> `prometheus_middleware` -> `add_trace_id`。
