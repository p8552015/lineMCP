## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - **實現 `/help` 指令**。它負責向用戶展示所有可用的指令，或特定指令的詳細用法。
    - **作為系統的「說明書」**。它是用戶了解系統功能的主要入口。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：**指令模式**中的一個具體**指令處理器 (Concrete Command Handler)**。
    - **上層來源**：
        1.  `domain.CommandExecutor`: 在接收到 `/help` 指令時，會找到並呼叫這個處理器。
        2.  `domain.command_registry`: 在啟動時會掃描並註冊這個處理器。
    - **下游依賴**：
        1.  `domain.command_registry`: 它反向依賴指令註冊表，以便獲取所有其他已註冊的指令來顯示它們的幫助訊息。這是一個**可控的、設計良好的「循環依賴」**，因為它只是為了查詢元數據，而不是執行功能。

- 🔁 **是否處理通訊 / 外部互動**：
    - **否**。它只處理內部狀態（從指令註冊表中讀取訊息）。

- ⚙️ **是否處理設定管理**：
    - **否**。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **是**。它的 `handle` 方法會解析傳入的 `args`，判斷用戶是想看所有指令的幫助，還是特定指令的幫助，這是一種**參數解析**。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是**。在 `_get_specific_command_help` 中，它使用了 `try...except KeyError` 來處理用戶查詢一個不存在的指令的情況，提供了友善的錯誤回饋。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **否**。

- 🎯 **實用比喻**：
    - 它就像是**博物館的導覽手冊或服務台**。當遊客（用戶）詢問「這裡有什麼？」 (`/help`)，服務台會給出一份包含所有展廳（指令）列表和簡介的地圖。如果遊客詢問「『恐龍化石』展廳在哪裡？」 (`/help dinosaur`)，服務台會提供該展廳的詳細位置、展品介紹和參觀路線。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`HelpCommandHandler`
- 📌 **創建目的**：
    - 專門處理 `/help` 指令的邏輯，將其與其他指令的邏輯完全分離。
- 🧭 **使用場景（由誰使用、何時初始化）**：
    - **由誰使用**：由 `CommandExecutor` 呼叫。
    - **何時初始化**：在應用啟動時，由指令註冊表自動發現並實例化。
- 📂 **管理資源**：
    - 不管理任何外部資源。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `command_name`, `description`, `aliases`, `get_usage`: 實現了 `CommandHandler` 抽象介面，提供了指令的元數據。
    - `handle()`: 指令處理的入口點，根據參數選擇不同的幫助訊息生成策略。
    - `_get_specific_command_help()`: 生成單一指令的詳細幫助。
    - `_get_all_commands_help()`: 生成所有指令的概覽幫助。
- 🔄 **是否支援擴充或注入**：
    - **是**。它接收 `CommandContext` 的注入，雖然在這個具體的指令中沒有使用，但遵循了統一的模式。
- 💡 **設計考量**：
    - **SRP**: 職責非常單一：提供幫助訊息。
    - **開閉原則 (Open/Closed Principle)**：當系統中新增或刪除其他指令時，這個 `HelpCommandHandler` **不需要做任何修改**。它總是動態地從指令註冊表中獲取最新的指令列表，這是一個非常優秀的設計。
    - **代碼可讀性**: 將生成不同幫助訊息的邏輯拆分到私有方法中，提高了可讀性。
