# 檔案分析報告：`apps/bot/src/services/nl_to_sql/interfaces/parsing_interfaces.py`

## 1. 檔案目的與角色

此檔案是 NL-to-SQL 新 SOLID 架構的**契約定義中心**，專門負責**解析**這一環節。它不包含任何具體的業務邏輯實作，而是透過定義一系列抽象基底類別 (ABC)，為解析器、解析策略和解析器工廠建立了清晰、穩定且可擴展的藍圖。

它在架構中的核心角色是：
1.  **實施介面隔離原則 (ISP)**: 透過細粒度的介面（`IParser`, `IParsingStrategy`），確保客戶端只需依賴它們真正需要的功能。
2.  **貫徹依賴倒置原則 (DIP)**: 讓高層模組（例如 `NaturalLanguageToSQLService` 包裝器）依賴於此處定義的抽象介面，而不是任何具體的解析器實作。
3.  **奠定架構的靈活性與可擴展性**: 透過策略模式和工廠模式的介面設計，為未來新增解析算法或解析器類型提供了無需修改現有程式碼的可能性。

簡而言之，這個檔案是整個解析次系統（parsing subsystem）的基石和法律。

## 2. 主要類別/函數定義

此檔案定義了三個抽象基底類別 (Interface)，它們共同構成了解析功能的骨架。

### `class IParser(ABC)`
*   **職責**: 定義了一個「解析器」應該具備的核心能力。任何想要承擔「將自然語言轉換為結構化查詢」職責的類別，都必須簽署並履行這份契約。
*   **核心方法**:
    *   `parse(...) -> ParsedQuery`: 主要的執行方法，負責執行解析。
    *   `can_handle(...) -> float`: 一個快速的自我評估方法，用來判斷自己處理特定文字的信心，為解析器的動態選擇提供了依據。
    *   `get_parser_info() -> dict`: 提供元資料，讓系統可以了解解析器的身份和能力。

### `class IParsingStrategy(ABC)`
*   **職責**: 定義了單一「解析策略」的介面。這是實現**策略模式 (Strategy Pattern)** 的關鍵。它允許將不同的解析演算法（如規則型、AI 型、混合型）封裝成可互換的策略物件。
*   **核心方法**:
    *   `execute_strategy(...) -> ParsedQuery`: 執行該策略的具體演算法。
    *   `is_applicable(...) -> bool`: 判斷該策略是否適合處理當前的輸入。
    *   `get_priority() -> int`: 定義策略的優先級，當多個策略都適用時，系統可以依此進行選擇。

### `class IParserFactory(ABC)`
*   **職責**: 定義了「解析器工廠」的介面。它負責封裝創建和管理 `IParser` 物件的複雜邏輯，是**工廠模式 (Factory Pattern)** 的體現。
*   **核心方法**:
    *   `create_parser(...) -> IParser`: 根據指定的類型創建解析器實例。
    *   `register_parser_type(...)`: 提供了一個動態註冊新解析器類型的機制，極大地增強了系統的擴展性。
    *   `get_default_parser() -> IParser`: 獲取一個預設的解析器，簡化了普通情況下的使用。

## 3. 功能實現的簡要描述

這個檔案本身不實現任何功能，而是**描述了功能應該如何被實現**。它描繪了一個高度模組化和可組合的系統：
1.  系統中可以有多個 `IParser` 的實作。
2.  每個 `IParser` 的實作內部，可以持有多個 `IParsingStrategy` 的實作。
3.  當一個 `IParser` 需要解析文字時，它可以根據策略的 `is_applicable` 和 `get_priority` 方法，從其策略庫中選擇一個或多個最合適的策略來執行。
4.  而這些 `IParser` 物件由誰來創建和管理？答案是 `IParserFactory` 的實作。
5.  整個系統的最高層，只需要與 `IParserFactory` 互動，取得所需的解析器，然後呼叫其 `parse` 方法，無需關心背後複雜的策略選擇和物件創建過程。

## 4. 依賴關係

*   **`abc.ABC`, `abc.abstractmethod`**: 依賴 Python 的標準抽象基底類別工具來定義介面。
*   **`..models.query_models.ParsedQuery`**: 依賴於模型層定義的 `ParsedQuery` 資料結構。這是非常重要的架構特徵，表示**介面依賴於穩定的資料模型**，而不是任何具體的實作。

## 5. 設計模式與架構決策

這個檔案是設計模式的絕佳展示：
*   **策略模式 (Strategy Pattern)**: 透過 `IParsingStrategy` 介面清晰地定義。這是一個核心決策，旨在將演算法的變化與使用演算法的客戶端分離，從而提高靈活性和可維護性。
*   **工廠模式 (Factory Pattern)**: 透過 `IParserFactory` 介面定義。這個決策將物件的創建過程集中化和抽象化，使得客戶端代碼更加簡潔，並且易於更換或擴展新的產品（解析器）類型。
*   **介面隔離原則 (Interface Segregation Principle)**: 檔案將解析器、策略、工廠的介面清晰地分開，每個介面都只關注自己的職責，沒有包含任何不相關的方法。
*   **依賴倒置原則 (Dependency Inversion Principle)**: 這是整個檔案存在的基石。它迫使系統的高層模組（業務邏輯）依賴於這些抽象的介面，而不是底層的、易變的具體實作。

## 6. 潛在的改進點

作為一個介面定義檔案，它本身是相當完善和高級的。潛在的 "改進" 更像是對未來實作的一種期待或建議：
*   **契約的強制性**: Python 的抽象方法只能確保方法被實作，但無法強制 `docstring` 中提到的契約要求（如返回值範圍、執行時間等）。在具體的實作中，需要透過單元測試和程式碼審查來嚴格保證這些契約被遵守。
*   **非同步與同步**: 目前介面中的 `parse` 和 `execute_strategy` 都被定義為 `async`，這是一個重要的架acrhitectural決定，意味著整個解析流程被設計為非阻塞的。`can_handle` 則是同步的，這也是合理的，因為它應該是一個快速的檢查。在實作時需要嚴格遵守這一點。
