## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `EnhancedServiceFactory` 類別，它在整個應用程式中扮演**依賴注入 (DI) 容器**和**服務工廠 (Service Factory)** 的核心角色。
  - **核心職責**：
    1.  **服務註冊**: 在初始化時，透過一系列的 `register_*_services` 函式，將應用程式中所有可注入的服務（如資料庫服務、AI 模型服務等）及其生命週期（單例、瞬態）註冊到一個中央 `ServiceRegistry` 中。
    2.  **依賴解析與注入**: 根據服務之間的依賴關係，自動實例化並注入所需的依賴項。當一個服務被請求時，工廠會自動創建其所有依賴的服務。
    3.  **服務提供**: 提供 `get_service` 和 `get_required_service` 方法，讓應用程式的其他部分可以獲取所需的服務實例。
    4.  **循環依賴檢測**: 內建了循環依賴檢測機制 (`circular_dependency_detector`)，防止在服務解析過程中出現無限遞歸，提升了系統的強固性。

- 🧠 **在系統架構中的定位**:
  - **定位**：處於**基礎設施層 (Infrastructure Layer)** 的核心。它是應用程式中各個模組（特別是 `services` 和 `application` 層）之間的黏合劑，負責管理它們的生命週期和依賴關係。
  - **上層來源**：`src/routes/webhook.py` 等路由層檔案會呼叫它來獲取頂層的業務邏輯處理器（如 `MessageHandlerDI`）。
  - **下游依賴**：它依賴專案中幾乎所有的服務模組（如 `DatabaseService`, `EnhancedAIModelService` 等），因為它需要知道如何創建它們。

- 🔁 **是否處理通訊 / 外部互動**:
  - **否**。它本身不進行任何外部通訊，但它創建和管理負責通訊的服務（如 `OpenAIClient`, `DatabaseService`）。

- 🔐 **是否與授權、安全、敏感操作有關**:
  - **是**，間接相關。它負責實例化處理敏感資料的服務，但它本身不直接處理金鑰或憑證。安全實踐體現在它如何將設定（可能包含敏感資訊）注入到需要的服務中。

- 🎯 **實用比喻**:
  - 這個工廠就像一個高科技的**汽車組裝工廠**。它不親自製造任何零件（引擎、輪胎、車身），但它擁有一份詳細的藍圖（`ServiceRegistry`），知道如何將成千上萬的零件（各種服務）精確地組裝成一輛可以行駛的汽車（一個可運行的 `MessageHandlerDI`）。它還內建了品質檢測系統（循環依賴檢測），確保組裝過程不會出錯。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`EnhancedServiceFactory`
- 📌 **創建目的**:
  - 旨在實現**控制反轉 (Inversion of Control, IoC)** 和**依賴注入 (Dependency Injection, DI)** 設計模式。
  - 其核心目的是將**服務的創建**與**服務的使用**分離開來，從而降低模組間的耦合度，提高程式碼的可維護性、可擴展性和可測試性。
- 🧭 **使用場景**:
  - 在應用程式啟動時由 `webhook.py` 進行初始化 (`initialize`)。
  - 在每次處理 Webhook 請求時，`webhook.py` 會向它請求 `MessageHandlerDI` 服務來處理業務邏輯。
- 📂 **管理資源**:
  - 它不直接管理外部資源（如資料庫連線），但它管理著所有**服務物件的生命週期**。它可以根據註冊的作用域（`ServiceScope`）來決定一個服務實例是單例（Singleton，全局唯一）、瞬態（Transient，每次請求都新建）還是作用域（Scoped）。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `initialize()`: 註冊所有服務，建立服務提供者，是工廠的啟動方法。
  - `get_service()`: 獲取服務的核心方法，內含循環依賴檢測邏輯。
  - `create_message_handler()`: 一個便捷方法，專門用於創建應用程式最頂層的服務。
  - `get_dependency_health_report()`: 提供詳細的依賴健康報告，對於維護和除錯非常有價值。
  - `_register_*_services()`: 一系列的私有方法，用於模組化地註冊不同類型的服務。
- ⚙️ **是否耦合其他模組或設定來源**:
  - **是**，高度耦合。作為 DI 容器，它必須「知道」所有需要被管理的服務。從檔案開頭大量的 `import` 語句就可以看出這一點。然而，這種耦合是**受控且必要的**，是將耦合性集中在此處，以換取其他業務模組的解耦。
- 💡 **設計考量**:
  - **控制反轉 (IoC)**: 服務的依賴關係不再由服務自身創建，而是由工廠從外部「注入」，實現了控制權的反轉。
  - **單一職責原則 (SRP)**: 工廠的職責非常單一，就是管理服務的生命週期和依賴關係。
  - **可測試性**: 這是該設計帶來的最大好處之一。在測試中，可以輕易地建立一個新的工廠，並在其中註冊 Mock 或 Fake 的服務來取代真實的外部依賴（如資料庫），使得單元測試變得簡單可靠。

## 🧩 樣板 4：模組關係與相依

- **上游呼叫者**：`src/routes/webhook.py`
- **下游相依元件**：幾乎所有的 `src/services/` 和 `src/application/` 下的模組。它是整個服務依賴圖的根。
- **是否存在循環相依**：此模組本身透過 `circular_dependency_detector` 來**防止和檢測**下游模組間的循環依賴。這是其核心功能之一，也是一個非常成熟的設計。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：如上所述，此檔案本身是**故意設計成高耦合的**，它是一個「耦合中心」。這種模式的優點是將複雜性集中管理，只要此工廠的內部邏輯是穩定的，整個應用的其他部分就能維持低耦合。風險在於，隨著服務增多，此檔案會變得越來越複雜，需要良好的組織（如此處使用的模組化註冊函式 `register_*_services`）來維持可讀性。
- 🧪 **可測試性**：**極高**。該模式是實現高可測試性架構的關鍵。它允許在測試環境中替換任何服務的實現，從而可以隔離被測試的單元。
- 🧠 **重構潛力**:
  - 目前的設計已經非常先進和模組化。一個可能的優化方向是，考慮使用現成的、經過社群驗證的依賴注入框架（如 `dependency-injector`），這樣可以減少手動維護 `ServiceRegistry` 和 `ServiceProvider` 的程式碼，並獲得更豐富的功能（如非同步注入、配置管理等）。但目前的自訂實現提供了完全的控制權和高度的客製化能力。
