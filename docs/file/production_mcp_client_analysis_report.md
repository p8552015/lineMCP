## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - 作為應用程式與後端「工具服務」之間通訊的**具體執行者**。
    - 負責**啟動和管理**後端工具服務（如資料庫介面）的**子進程生命週期**。
    - 實現了基於**標準輸入/輸出 (`stdio`)** 的 **JSON-RPC** 通訊協議，負責發送指令、接收結果並處理通訊中的各種異常。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：處於軟體架構的**最底層**，是通往後端工具服務的**最終閘道**。
    - **上層來源**：其功能被 `UnifiedMCPClient` 代理和封裝，對上層業務邏輯（如 `DatabaseService`）隱藏了所有底層實現細節。
    - **下游依賴**：直接依賴作業系統的進程管理功能 (`asyncio.create_subprocess_exec`)，並與 `MCPConnectionPool` 緊密協作以監控和管理連接健康狀態。

- 🔁 **是否處理通訊 / 外部互動**：
    - **是**。這是它的核心職責。它專門處理與**本機子進程**之間基於 `stdio` 的非同步 I/O 通訊。

- ⚙️ **是否處理設定管理**：
    - **是**。它讀取 `mcp_config.py` 中的設定，以獲取啟動子進程所需的執行命令、路徑和環境變數。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **是**。它嚴格遵循 JSON-RPC 協議，負責：
        1.  將 `call_tool` 的請求**格式化**為 JSON-RPC 請求字串。
        2.  **解析**從子進程 `stdout` 讀取到的 JSON-RPC 回應。
        3.  透過 `_test_communication` 方法執行**通訊協定握手**，驗證連接是否成功建立。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是**，並且處理得非常好。
        - **平台相依性**：包含 `_apply_macos_hotfix` 方法，專門處理 macOS 平台上 `asyncio` 的 `Proactor` 事件循環問題，展現了其高度的工程嚴謹性。
        - **錯誤恢復**：整個類別的設計就是一個大型的錯誤恢復機制。它能監控進程健康 (`_verify_process_health`)，並在通訊失敗時通知 `MCPConnectionPool` 以觸發後續的恢復或重試邏輯。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **間接相關**。它負責將設定檔中可能包含的**敏感環境變數**（如 API 金鑰、資料庫密碼）安全地傳遞給隔離的子進程，避免了主應用程式直接持有這些敏感資訊。

- 🎯 **實用比喻**：
    - 它就像是**潛水艇的魚雷發射控制室**。艦橋（`UnifiedMCPClient`）下達「發射」的簡單指令，但控制室（`ProductionMCPClient`）負責所有複雜、危險且依賴物理平台的底層操作：打開魚雷管、壓力平衡、驗證系統、執行發射程序、監聽發射結果，並隨時準備處理卡彈或發射失敗等各種異常情況。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`ProductionMCPClient`
- 📌 **創建目的**：
    - 提供一個強健、可靠且高效的機制，來管理和操作與後端「工具服務」子進程之間的 `stdio` 通訊。其核心目的是**將複雜、不穩定且充滿細節的底層進程通訊徹底封裝起來**。
- 🧭 **使用場景（由誰使用、何時初始化）**：
    - **由誰使用**：僅由 `UnifiedMCPClient` 使用。
    - **何時初始化**：在應用程式生命週期中僅被初始化一次，當 `get_production_mcp_client()` 這個單例工廠函式首次被呼叫時創建。
- 📂 **管理資源**：
    - **核心資源**：管理 `asyncio.subprocess.Process` 物件，即**作業系統的子進程**。
    - **附帶資源**：管理子進程的 `stdin` 和 `stdout` **I/O 流**。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `connect_to_server`: 啟動子進程並執行通訊握手。
    - `call_tool`: 核心通訊方法，發送 JSON-RPC 請求並等待回應。
    - `_read_from_server`: 非同步讀取 `stdout` 的主循環。
    - `_verify_process_health`: 背景執行的健康檢查任務。
    - `close_all_connections`: 安全地終止所有子進程。
- 🔄 **是否支援擴充或注入**：
    - 不直接支援。它的擴充性體現在**數據驅動**上——可以透過修改 `mcp_config.py` 來增加新的後端工具服務，而無需修改其本身程式碼。
- ⚙️ **是否耦合其他模組或設定來源**：
    - **是**，與以下模組緊密耦合：
        1.  `mcp_config.py` (設定來源)
        2.  `MCPConnectionPool` (健康與恢復策略)
        3.  `asyncio` (底層執行框架)
- 💡 **設計考量（如封裝、SRP、DI、可測試性）**：
    - **封裝 (Encapsulation)**：設計的**首要目標**。完美地隱藏了所有關於異步、進程管理、平台修復和協議處理的細節。
    - **SRP (單一職責原則)**：職責非常清晰：管理與子進程的 `stdio` **通訊鏈路**。它將健康狀態的**評估策略**和**統計**職責分離給了 `MCPConnectionPool`。
    - **DI (依賴注入)**：在 `__init__` 中接收 `MCPConnectionPool` 的實例，遵循了依賴注入原則。
- ✅ **是否容易測試 / 是否有測試機制設計**：
    - **是**，可測試性很高。可以透過 Mock `asyncio.create_subprocess_exec` 來提供一個模擬的子進程，該進程可根據測試案例的需要在其 `stdin` 上接收數據並向其 `stdout` 寫入預設的回應，從而可以對 `ProductionMCPClient` 的所有邏輯進行單元測試。

【補充分析】
- 🔄 **是否支援 retry / fallback / timeout**：
    - **Retry/Fallback**: 本身不直接實現重試邏輯，但它與 `MCPConnectionPool` 協作。當 `call_tool` 失敗時，它會呼叫 `pool.record_failure()`，這可能觸發連接池層面的恢復或重試策略。
    - **Timeout**: 在 `call_tool` 中，對 `self.events[request_id].wait()` 的呼叫隱含了超時機制（由 `mcp_config` 的 `timeout_seconds` 控制），防止無限等待。
- 🔁 **是否非同步 async / 並行 queue / 多線程保護**：
    - **完全非同步**：整個類別基於 `asyncio` 設計，所有 I/O 操作都是非阻塞的。
    - **並行安全**: 透過 `asyncio.Lock` 保護對共享資源（如 `self.processes` 字典）的訪問，確保在並行環境下的線程安全。
- 📊 **測試覆蓋情況（若已知）**：未知。但其結構設計良好，具備高可測試性。
- 🚨 **是否為效能瓶頸或熱點**：不是瓶頸。作為 I/O 密集型任務，它使用 `asyncio`，效率極高。真正的效能取決於其啟動的後端子進程。
- 🧼 **是否有清理 / close / dispose 等機制**：
    - **是**，非常完善。`close_all_connections` 和 `_cleanup_process` 確保了所有管理的子進程在應用程式關閉或自身終止時都能被安全地清理。

## 🧩 樣板 4：模組關係與相依

- **上游呼叫者（誰依賴此模組？）**
    - 唯一的直接上游是 `unified_mcp_client.py`。業務邏輯層不應也無法直接與之互動。

- **下游相依元件（此模組依賴哪些外部資源/API？）**
    - `mcp_connection_pool.py`: 依賴其進行健康狀態的統計與回報。
    - `mcp_config.py`: 依賴其提供啟動設定。
    - `Python asyncio` 函式庫: 整個模組的運作基礎。
    - 作業系統進程 API: 依賴其來實際創建和管理子進程。

- **是否存在循環相依（circular dependency）？**
    - **否**。依賴關係是清晰的單向流：`業務邏輯 -> UnifiedMCPClient -> ProductionMCPClient -> MCPConnectionPool`，沒有反向依賴。

## 🧱 額外架構師視角建議補充欄位

- 🧩 **模組相依關係圖**：
    `[DatabaseService] --> [UnifiedMCPClient] --(代理)--> [ProductionMCPClient] --(回報健康狀態)--> [MCPConnectionPool]`

- 🗂️ **是否有循環相依 / 高耦合風險**：
    - 無循環依賴。與 `mcp_config` 和 `MCPConnectionPool` 的耦合是必要的，因為它的職責就是實現這兩者所定義的策略和設定。這種耦合是受控且職責清晰的。

- ☁️ **是否容器化部署友善**：
    - **是**，非常友善。由於它依賴的是與主應用程式在同一個文件系統內的腳本，只要這些腳本與主應用程式一起被打包到 Docker image 中，它就能在容器環境中無縫運作。

- 🔐 **是否含權限機制、金鑰管理或機敏資料處理**：
    - 它本身不處理權限，但它是一個**安全的金鑰傳遞者**。它從設定檔中讀取敏感的環境變數，並將它們僅注入到目標子進程中，這是實現**最小權限原則**的良好實踐。

- 🧪 **可測試性**：
    - **高**。如前所述，依賴注入和清晰的職責劃分使其易於透過 Mock 和模擬 `stdio` 流進行測試。

- ♻️ **是否為共享模組（utility）或純服務模組（service）**：
    - 是一個**純粹的底層基礎設施服務模組 (Infrastructure Service)**。它的存在就是為了提供一個非常具體的技術能力。

- 🧠 **能否重構為 microservice 或 reusable package**：
    - **可以**。這個模組（連同 `MCPConnectionPool` 和 `UnifiedMCPClient`）的設計非常通用，完全有潛力被提取出來，成為一個獨立的、可重用的 Python 套件 (`pip install mcp-client`)，專門用於處理基於 `stdio` 的 JSON-RPC 子進程通訊。
