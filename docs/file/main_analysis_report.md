## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - 作為 **FastAPI Web 應用程式的進入點**。
    - 負責**初始化和設定**整個應用程式，包括伺服器實例、中介軟體、路由和生命週期事件。
    - 整合核心服務，如可觀測性 (Observability)、Redis 連線，並掛載監控端點。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：處於整個專案的**最高層和啟動層**。
    - **上層來源**：由 ASGI 伺服器（如 Uvicorn）載入和執行。
    - **下游依賴**：
        1.  `routes.webhook`: 引入並註冊核心的 Webhook 路由。
        2.  `middleware`: 引入並設定中介軟體。
        3.  `utils.observability`, `utils.redis_client`: 引入並在應用程式生命週期中設定和關閉這些基礎服務。
        4.  `config`: 獲取應用程式設定。
        5.  `prometheus_client`, `opentelemetry`: 引入第三方函式庫以設定監控和追蹤。

- 🔁 **是否處理通訊 / 外部互動**：
    - **是**。它在啟動時會嘗試與 **Redis** 進行 ping/pong 通訊以驗證連線。

- ⚙️ **是否處理設定管理**：
    - **是**。它呼叫 `config.get_settings()` 來載入全域應用程式設定。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **否**。它只負責設定和路由分發，不直接處理業務資料。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是**。它定義了一個**全域例外處理器** (`global_exception_handler`)，作為最後一道防線，捕捉所有未被處理的例外，記錄日誌並回傳標準化的 500 錯誤，這是一種重要的錯誤恢復機制。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **否**。安全相關的邏輯（如簽名驗證）被委託給了下游的 `middleware` 或路由層。

- 🎯 **實用比喻**：
    - 它就像是**一棟大樓的總開關和接待大廳**。它負責在「開門營業」(`lifespan` 啟動) 時打開所有必要的設施（接通 Redis、設定好監控），然後將訪客（網路請求）引導到正確的部門（`webhook` 路由）。它還在大門口設定了保全（全域例外處理器），以處理意外事件。
