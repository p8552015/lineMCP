## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - 作為一個**穩定的抽象層**，為應用程式的其他部分提供一個**統一且不變的介面**來與後端的「主控協議」(MCP) 服務互動。
    - 其核心責任是**解耦**上層的業務邏輯與下層的通訊實現細節。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：處於軟體架構的**中間抽象層**。
    - **上層來源**：被所有需要與 MCP 互動的服務所依賴，最主要的呼叫者是 `DatabaseService`。
    - **下游依賴**：它依賴並代理 (Proxy) `ProductionMCPClient`，將所有實際工作都委託給它。

- 🔁 **是否處理通訊 / 外部互動**：
    - **否**。它本身不處理任何通訊，而是將通訊請求**完全轉發**給下游的 `ProductionMCPClient`。

- ⚙️ **是否處理設定管理**：
    - **否**。它不關心任何設定，這使得它的介面更加乾淨和穩定。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **否**。它是一個純粹的**傳遞者 (Pass-through)**，不對資料進行任何形式的處理。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **否**。它的一個重要價值就是**隱藏**這些複雜性。所有這些問題都由它所代理的 `ProductionMCPClient` 來處理。

- 🔐 **是否與授權、安全、敏感操作有關**：
    - **否**。

- 🎯 **實用比喻**：
    - 它就像是一個**外交部或大使館**。國內各部門（業務邏輯）只需要向外交部提出統一格式的請求（例如「與 A 國建立通商」），而無需關心 A 國的語言、文化和辦事流程。外交部（`UnifiedMCPClient`）會將請求轉交給駐 A 國的大使（`ProductionMCPClient`），由大使來處理所有具體的、當地化的溝通細節。如果未來與 A 國的溝通方式改變了（例如從電報變成視訊會議），國內部門完全無感，因為他們面對的仍然是穩定不變的外交部。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`UnifiedMCPClient`
- 📌 **創建目的**：
    - 遵循**依賴反轉原則 (Dependency Inversion Principle)**。它的存在是為了讓高層模組（如業務邏輯）不直接依賴於低層模組（如 `stdio` 通訊實現），而是兩者都依賴於這個**抽象** (`UnifiedMCPClient`)。
- 🧭 **使用場景（由誰使用、何時初始化）**：
    - **由誰使用**：由任何需要呼叫 MCP 工具的服務使用，主要是 `DatabaseService`。
    - **何時初始化**：在應用程式生命週期中僅被初始化一次，當 `get_unified_mcp_client()` 這個單例工廠函式首次被呼叫時創建。
- 📂 **管理資源**：
    - 它**不直接管理**任何資源。它持有一個對 `ProductionMCPClient` 的引用，由後者來管理實際的子進程和 I/O 資源。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `call_tool(self, server_name: str, tool_name: str, parameters: dict, timeout: int = 30) -> dict`: 將呼叫轉發給 `_production_client`。
    - `list_tools(self, server_name: str, timeout: int = 10) -> list`: 將呼叫轉發給 `_production_client`。
    - `close_all_connections(self)`: 將呼叫轉發給 `_production_client`。
    - 所有方法的邏輯都極其簡單：`return self._production_client.method(...)`。
- 🔄 **是否支援擴充或注入**：
    - 其設計本身就是為了**被注入**到其他服務中。它的擴充性體現在：可以輕易地在 `__init__` 中將 `_production_client` 替換為另一個實現（如 `StagingMCPClient` 或 `MockMCPClient`），而上層呼叫者完全不受影響。
- ⚙️ **是否耦合其他模組或設定來源**：
    - **是**，它唯一耦合的模組就是 `production_mcp_client.py`。
- 💡 **設計考量（如封裝、SRP、DI、可測試性）**：
    - **設計模式**: 完美體現了**代理模式 (Proxy Pattern)** 和**外觀模式 (Facade Pattern)**。
    - **SRP (單一職責原則)**：職責極其單一：提供一個穩定的代理介面。
    - **DI (依賴注入)**：它自身就是被注入到其他服務中的依賴項。
    - **可測試性**: 這是它存在的核心價值之一。
- ✅ **是否容易測試 / 是否有測試機制設計**：
    - **非常容易**。在單元測試中，可以極其簡單地 Mock `get_unified_mcp_client()` 回傳一個假的 Client 物件，從而將所有需要與後端 MCP 互動的服務與實際的通訊層完全隔離。

## 🧱 額外架構師視角建議補充欄位

- 🧩 **模組相依關係圖**：
    `[DatabaseService] --(依賴注入)--> [UnifiedMCPClient] --(代理)--> [ProductionMCPClient]`

- 🗂️ **是否有循環相依 / 高耦合風險**：
    - 無循環依賴。它與 `ProductionMCPClient` 的耦合是其設計的核心，但這是一種**向著穩定方向的耦合**。

- ☁️ **是否容器化部署友善**：
    - 是。它對部署環境完全不敏感。

- 🔐 **是否含權限機制、金鑰管理或機敏資料處理**：
    - 否。

- 🧪 **可測試性**：
    - **極高**。這是它存在的核心價值之一，使得上層業務邏輯的單元測試變得極其簡單。

- ♻️ **是否為共享模組（utility）或純服務模組（service）**：
    - 它是一個純粹的**抽象服務模組 (Abstract Service)**，其價值在於其定義的介面而非其實現。

- 🧠 **能否重構為 microservice 或 reusable package**：
    - 它應該與 `ProductionMCPClient` 一起被打包到可重用的 `mcp-client` 套件中，作為該套件的**推薦公開 API**。
