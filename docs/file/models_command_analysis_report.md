## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**：
    - **實現 `/models` 指令**。它提供兩種核心功能：列出所有可用的 AI 模型，或者顯示單一指定模型的詳細資訊。
    - **作為 AI 服務的可觀測性介面**。讓用戶或管理員能夠了解系統當前配置了哪些 AI 模型、哪個是正在使用的，以及它們的狀態和能力。

- 🧠 **在系統架構中的定位（上層來源與下游依賴）**：
    - **定位**：**指令模式**中的一個具體**指令處理器 (Concrete Command Handler)**。
    - **上層來源**：被 `domain.CommandExecutor` 在用戶輸入 `/models` 時呼叫。
    - **下游依賴**：
        1.  `domain.CommandContext`: 強烈依賴指令上下文來獲取 `ai_model_service`。此指令的所有數據都源自於這個服務。

- 🔁 **是否處理通訊 / 外部互動**：
    - **否**。它將所有與 AI 服務的互動都委託給了注入的 `ai_model_service`，自身不處理通訊細節。

- ⚙️ **是否處理設定管理**：
    - **否**。

- 🧪 **是否負責資料驗證、格式轉換或協定解析**：
    - **是**。
        1.  `handle` 方法**解析**指令參數 (`args`) 來決定執行哪個子功能（列表或詳情）。
        2.  `_format_models_list` 和 `_format_model_details` 方法將從 AI 服務獲取的結構化數據（字典列表）**轉換**為對用戶友善的、格式化的文字訊息。

- 💡 **是否涉及平台相依性、跨平台兼容性、錯誤恢復**：
    - **是，而且設計得非常出色**。
        1.  **錯誤恢復**：在 `handle`, `_list_all_models`, `_get_model_details` 方法中都有 `try...except` 區塊，能夠優雅地處理從 AI 服務獲取資訊時可能發生的任何失敗。
        2.  **兼容性/穩健性**：`_get_models_from_service` 方法是一個**極佳的防禦性編程範例**。它不假設 `ai_model_service` 只有一種實現方式，而是依次嘗試多種方式 (`hasattr(...)`) 來獲取模型列表和當前模型。這使得此指令對於未來 `ai_model_service` 的重構或替換具有很強的**適應能力**。

- 🎯 **實用比喻**：
    - 它就像是**一個應用程式商店的客戶端**（例如 `pip` 或 `npm` CLI）。你可以用 `pip list` 來列出所有已安裝的套件（`/models`），或者用 `pip show <package>` 來查看某個特定套件的詳細資訊（`/models <model_name>`）。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- **類別名稱**：`ModelsCommandHandler`
- 📌 **創建目的**：
    - 專門封裝所有與 AI 模型資訊查詢、過濾和格式化相關的邏輯。
- 🧭 **使用場景**：由 `CommandExecutor` 呼叫。
- 📂 **管理資源**：不管理任何外部資源。
- 🧩 **內含哪些關鍵方法與邏輯功能**：
    - `handle()`: 指令的入口和路由器。
    - `_list_all_models()`: 獲取並格式化所有模型的列表。
    - `_get_model_details()`: 尋找並格式化單一模型的詳細資訊。
    - `_get_models_from_service()`: **核心的數據獲取方法**。以一種非常穩健和兼容的方式從 AI 服務中提取數據。
    - `_format_models_list()`, `_format_model_details()`: **表現層方法**。負責將數據美化成最終的輸出。
- 💡 **設計考量**：
    - **SRP**: 職責非常單一，只關心 AI 模型的資訊展示。
    - **防禦性編程**: `_get_models_from_service` 的設計是其最大的亮點，體現了對未來變化（`ai_model_service` 介面變動）的考慮。
    - **關注點分離**: 同樣，將數據獲取、業務邏輯（尋找模型）和數據展示清晰地分離在不同的方法中。
