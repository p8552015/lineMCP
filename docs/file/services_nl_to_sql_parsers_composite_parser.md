# 檔案分析報告：`apps/bot/src/services/nl_to_sql/parsers/composite_parser.py`

## 1. 檔案目的與角色

此檔案是 NL-to-SQL 新架構中**解析層的總指揮和協調者**。它自身不執行任何具體的解析邏輯，而是扮演著一個**智能策略路由器**的角色。

它的核心職責是管理一組不同的解析器（如 `RuleBasedParser`, `AIEnhancedParser`），並根據每個解析器對當前輸入的「信心」，動態地選擇最合適的一個來處理請求。

它在架構中的角色是：
1.  **統一入口 (Unified Entry Point)**: 對於上層服務來說，它就是唯一的 `IParser`。這隱藏了內部存在多個解析器的複雜性。
2.  **決策引擎 (Decision Engine)**: 根據各個子解析器的 `can_handle` 回傳值和預設權重，執行策略選擇。
3.  **能力聚合器 (Capability Aggregator)**: 將多個專注於不同領域的解析器的能力，聚合成一個單一的、更強大、更全面的解析服務。

這個檔案是**組合模式**和**策略模式**的完美結合，是整個解析層能夠協同工作、兼顧效能與智能的關鍵。

## 2. 主要類別/函數定義

### `class CompositeParser(IParser)`
這是此檔案中唯一定義的類別。它自身實現了 `IParser` 介面，使其能夠像一個普通的解析器一樣被使用，同時它又包含了一組其他的 `IParser` 物件。

#### 核心方法

*   **`__init__(self)`**:
    初始化一個空的解析器列表 `_parsers` 和一個策略權重字典 `_strategy_weights`。

*   **`add_parser(self, parser: IParser, weight: float = 1.0)`**:
    此方法允許在執行時動態地向組合解析器中**註冊**一個新的解析器策略。`weight` 參數提供了一種微調解析器優先級的手段。

*   **`remove_parser(self, parser_class_name: str)`**:
    允許動態地移除一個已註冊的解析器。

*   **`async parse(self, text: str, ...)`**:
    這是核心的協調邏輯，體現了其作為決策引擎的職責：
    1.  **評估 (Evaluate)**: 首先呼叫 `_evaluate_parser_capabilities`，此方法會非同步地（如果需要）遍歷所有子解析器，並收集它們各自對當前 `text` 的 `can_handle` 分數。
    2.  **選擇 (Select)**: 接著呼叫 `_select_best_parser`，根據上一步收集的分數和預設的權重，計算出每個解析器的最終得分，並選出得分最高的一個。
    3.  **執行 (Execute)**: 最後，只呼叫被選中的那一個「最佳」解析器的 `parse` 方法來完成實際的解析工作。
    4.  **增強 (Enhance)**: 它會對返回的 `ParsedQuery` 進行增強，在 `explanation` 中註明是由哪個解析器處理的，並根據權重微調信心度。

*   **`can_handle(self, text: str) -> float`**:
    它不只是返回某一個子解析器的信心度，而是計算所有子解析器信心度的**加權平均值**，從而給出一個更能代表整體能力的綜合評分。

## 3. 功能實現的簡要描述

`CompositeParser` 的工作流程就像一個經驗豐富的專案經理：
1.  **組建團隊**: 透過 `add_parser` 方法，它招募了幾個具有不同專長的團隊成員（`RuleBasedParser` 擅長快速處理標準流程，`AIEnhancedParser` 擅長應對複雜的創意挑戰）。
2.  **接收任務**: 接到一個新任務（一個自然語言字串）。
3.  **快速評估**: 它不會立即把任務交給某個人，而是先問團隊中的每一個人：「嘿，你對搞定這個任務有多大把握？」(呼叫每個 parser 的 `can_handle` 方法)。
4.  **權衡決策**: 它根據每個人的回覆，結合自己對他們能力的了解（預設的 `weight`），在心中計算出誰是當前任務的最佳人選。
5.  **委派任務**: 它只把任務明確地指派給那個最佳人選（呼叫 `best_parser.parse`）。
6.  **匯報總結**: 拿到結果後，它會稍作修飾（在解釋中加上是誰完成的），然後向上級（呼叫者）匯報。

## 5. 設計模式與架構決策

*   **組合模式 (Composite Pattern)**: 這是該類別的結構基礎。它使得單一物件（如 `RuleBasedParser`）和複合物件（`CompositeParser`）可以被一致地對待。
*   **策略模式 (Strategy Pattern)**: 每個被加入的子解析器都扮演著一個「策略」的角色。`CompositeParser` 則是管理和選擇這些策略的上下文（Context）。
*   **責任鏈模式 (Chain of Responsibility) 的變體**: 雖然不是典型的依次傳遞，但其「選擇一個處理者」的思想與責任鏈模式非常相似，是一種更主動、更智能的責任鏈。
*   **開閉原則 (OCP)**: 這是此設計帶來的最大好處。當需要引入新的解析能力時，只需開發一個新的 `IParser` 實現，並將其註冊到 `CompositeParser` 中即可，無需修改 `CompositeParser` 或任何現有解析器的程式碼。
*   **單一職責原則 (SRP)**: 它自身嚴格遵守單一職責，只負責「協調」，而不負責「解析」，使得程式碼非常內聚和清晰。

## 6. 潛在的改進點

*   **複雜的選擇策略**: 目前的選擇策略是基於加權信心度選出「唯一最佳」。在更複雜的場景中，可以擴展選擇策略，例如：
    *   **結果融合**: 允許多個解析器同時執行，然後對它們的結果進行融合或投票。
    *   **兩階段確認**: 先用規則解析器提取實體，再將提取出的實體交給 AI 解析器進行意圖判斷。
*   **迴圈依賴**: 需要在註冊時防止迴圈依賴（例如，一個 `CompositeParser` 實例被加入到它自己的子解析器列表中）。目前的程式碼沒有這個檢查，但可以輕易加入。
*   **並行評估**: `_evaluate_parser_capabilities` 方法可以透過 `asyncio.gather` 來並行執行所有 `can_handle` 的呼叫（儘管 `can_handle` 被設計為快速的同步方法，但如果未來有非同步的 `can_handle` 實現，這一點會很重要）。
