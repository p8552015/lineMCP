## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `StatusCommandHandler` 類別，是一個具體的指令處理器，專門負責處理 `/status` 指令。
  - **核心職責**：作為一個**健康檢查聚合器 (Health Check Aggregator)**。它會依序檢查系統中各個關鍵依賴和服務的狀態，並生成一份匯總的報告。檢查的服務包括：
    1.  **MCP 連接**: 透過執行一個簡單的 `SELECT 1` 查詢來測試與後端 MCP `postgres` 工具的連通性。
    2.  **AI 服務**: 檢查 AI 服務是否已成功載入。
    3.  **資料庫服務**: 檢查資料庫服務是否已初始化。
    4.  **內部核心服務**: 檢查 `CommandContext` 中其他的服務（如自然語言服務、格式化器）是否可用。

- 🧠 **在系統架構中的定位**:
  - **定位**：在 `commands` 模組中，它是一個**內部監控與診斷工具**。它提供了一個從外部（聊天介面）觸發內部健康檢查的能力，對於快速排查問題非常有用。
  - **上層來源**：由 `CommandExecutor` 在解析到 `/status` 指令時調用。
  - **下游依賴**：`CommandContext`。它嚴重依賴 `CommandContext` 來獲取所有需要檢查的服務實例。

- 🎯 **實用比喻**:
  - `StatusCommandHandler` 就像是汽車儀表板上的**「系統檢查」按鈕**。當你按下這個按鈕時，汽車的行車電腦會快速地檢查引擎、煞車、輪胎壓力、油量等各個子系統的狀態，然後在螢幕上給你一個清晰的報告（例如，「所有系統正常」或「輪胎壓力不足」），讓你對汽車的整體健康狀況一目了然。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`StatusCommandHandler`
- 📌 **創建目的**:
  - **核心目的**：提供一個**單點的、非侵入式**的方式來監控整個應用程式的健康狀況。
  - **具體目的**：讓開發者或管理員無需登入伺服器、查看日誌，就能快速判斷系統當前的服務可用性，定位潛在問題點。
- 🧭 **使用場景**:
  - 當感覺系統回應異常時，用來做初步的問題排查。
  - 作為日常的例行健康檢查。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `handle()`: 呼叫 `_perform_status_checks` 執行所有檢查，然後呼叫 `_format_status_report` 將結果格式化成訊息。
  - `_perform_status_checks()`: 聚合器方法，依序呼叫各個具體的檢查函式。
  - `_check_*()`: 一系列私有的、職責單一的檢查函式，每個函式負責檢查一個特定的服務。這種設計使得新增一個新的檢查項變得非常容易。
  - `_format_status_report()`: 負責將結構化的檢查結果（一個字典）轉換為易於閱讀、帶有狀態圖示（✅⚠️❌）的文本訊息。
- 💡 **設計考量**:
  - **聚合模式 (Aggregation Pattern)**: `_perform_status_checks` 聚合了多個子檢查的結果。
  - **關注點分離**: 將「執行檢查」 (`_perform_status_checks`) 和「格式化報告」 (`_format_status_report`) 分離。同時，將對每個服務的具體檢查邏輯也分離到各自的 `_check_*` 方法中，可讀性和可維護性都很好。
  - **防禦性編程**: 每個 `_check_*` 方法內部都有 `try...except` 區塊。即使某個服務的檢查過程本身就拋出異常（例如，MCP 連接超時），也不會中斷整個狀態檢查流程，而是會將該項標記為錯誤，並繼續檢查其他服務。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。它只依賴於 `CommandContext`，這正是 `CommandContext` 設計的目的——傳遞共享依賴。
- 🧪 **可測試性**：**高**。在測試中，可以創建一個 Mock 的 `CommandContext`，並為其中的每個服務屬性分配 Mock 物件。然後可以透過控制這些 Mock 物件的行為（例如，讓 `mcp_client.call_tool` 拋出異常）來模擬各種健康或異常狀態，並驗證 `StatusCommandHandler` 是否能生成預期中的報告。
- 🧠 **重構潛力**:
  - **可插拔的健康檢查**: 目前的 `_perform_status_checks` 方法是硬編碼呼叫各個檢查函式。一個更進階的設計是建立一個「健康檢查項」的註冊表。可以定義一個 `IHealthCheck` 介面，然後讓各個服務自己實現這個介面。`StatusCommandHandler` 在執行時，只需從註冊表中獲取所有 `IHealthCheck` 的實例並依次執行即可。這樣，當新增一個服務時，只需讓它實現 `IHealthCheck` 介面並註冊自己，就自動被納入狀態檢查的範圍，無需再修改 `StatusCommandHandler` 的程式碼。
  - **非同步執行**: `_perform_status_checks` 中的各項檢查是**依序**執行的 (`await self._check_mcp_connection()`)。如果未來檢查項增多，或者某些檢查項比較耗時，可以考慮使用 `asyncio.gather` 來**並行**執行所有的檢查，以縮短 `/status` 指令的總體回應時間。
