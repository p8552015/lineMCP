## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `SqlCommandHandler` 類別，它是**一個具體的指令處理器**，專門負責處理 `/sql` 指令。
  - **核心職責**：
    1.  **接收 SQL 查詢**: 接收使用者透過指令傳入的原始 SQL 查詢字串。
    2.  **參數驗證**: 對傳入的 SQL 語句進行基礎的**安全性驗證** (`validate_args`)，例如檢查是否為空、是否包含 `DROP`, `DELETE` 等不被允許的危險關鍵字。
    3.  **執行查詢**: 透過 `CommandContext` 獲取 MCP (Master Control Program) 客戶端，並將 SQL 語句發送給後端的 `postgres` 工具執行。
    4.  **結果解析與格式化**: 接收後端回傳的結果，使用 `MCPResponseParser` 進行解析，並將結果格式化為人類可讀的文本訊息（`TextMessage`）回傳給使用者。
    5.  **錯誤處理**: 捕獲執行過程中的例外，並將其包裝成一個領域特定的異常 (`create_db_error`) 向上拋出，由統一的錯誤處理機制來處理。

- 🧠 **在系統架構中的定位**:
  - **定位**：在 `commands` 模組中，它是一個**具體的業務邏輯實現單元**。它響應一個特定的使用者意圖（「我想直接執行SQL」）。
  - **上層來源**：由 `CommandExecutor` 在解析到 `/sql` 指令時，從 `CommandRegistry` 中查找到並調用其 `handle` 方法。
  - **下游依賴**：
    - `CommandContext`: 獲取 MCP 客戶端等共享服務。
    - `MCPResponseParser`: 解析 MCP 回傳的結果。
    - `create_db_error`: 建立領域異常。

- 🔐 **是否與授權、安全、敏感操作有關**:
  - **是，高度相關**。它直接處理使用者輸入的 SQL。雖然它實現了基礎的關鍵字黑名單驗證，但這依然是一個潛在的安全風險點。允許使用者直接執行 SQL 是一個需要非常謹慎對待的功能。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`SqlCommandHandler`
- 📌 **創建目的**:
  - **核心目的**：提供一個讓進階使用者或開發者能夠**直接與資料庫互動**的快速通道，用於調試、資料查詢或執行一些 NL-to-SQL 無法輕易表達的複雜查詢。
- 🧭 **使用場景**:
  - 當使用者在聊天視窗中輸入 `/sql SELECT ...` 時被觸發。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `command_name`, `description`, `aliases`, `get_usage()`: 實現了 `CommandHandler` 的契約，提供指令的元數據。
  - `validate_args()`: 實現了對 SQL 查詢的**前置安全檢查**。這是防止明顯惡意查詢的第一道防線。
  - `handle()`: 核心業務邏輯，實現了「獲取 MCP 客戶端 -> 執行 -> 解析 -> 格式化」的完整流程。
  - `_format_sql_result()`: 一個輔助方法，專門負責將結構化的資料陣列轉換成易於在聊天視窗中閱讀的文本格式。
- 💡 **設計考量**:
  - **關注點分離**: `handle` 方法清晰地展示了業務流程，而將結果的解析和格式化分別委派給了 `MCPResponseParser` 和 `_format_sql_result`，保持了主流程的簡潔。
  - **領域異常**: 在 `except` 區塊中，它沒有直接處理錯誤，而是將其轉換為一個更具語意的領域異常 (`DbError`) 向上拋出。這使得上層的錯誤處理器可以根據異常類型做出更精確的響應。
  - **安全性**: `validate_args` 的實現表明開發者對此功能的潛在風險有清醒的認識，並採取了基礎的防護措施。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。作為指令模式的一個具體實現，它與調用者完全解耦。它與下游的 `MCPResponseParser` 有耦合，但這是一個合理的、功能性的依賴。
- 🧪 **可測試性**：**高**。在單元測試中，可以：
    1.  為其提供一個 Mock 的 `CommandContext`。
    2.  讓 Mock 的 `get_mcp_client` 方法回傳一個 Mock 的 MCP 客戶端。
    3.  設置 Mock 的 MCP 客戶端的 `call_tool` 方法回傳各種模擬的成功或失敗結果。
    4.  驗證 `handle` 方法是否能正確地解析結果、格式化訊息，或在失敗時拋出預期的異常。
- 🧠 **重構潛力**:
  - **增強安全驗證**: 目前的關鍵字黑名單過於簡單，容易被繞過（例如，`'dr'+'op'`）。一個更安全的方法是使用一個真正的 SQL 解析庫（如 `sqlparse`）來解析使用者的輸入。首先將 SQL 解析成語法樹，然後檢查語法樹的類型是否為 `SELECT`。這可以從根本上杜絕所有非查詢類型的語句，遠比關鍵字過濾安全。
  - **權限控制**: `/sql` 是一個非常強大的指令。未來應該引入權限控制機制，只允許特定身份（如管理員）的使用者執行此指令。這個邏輯可以加在 `handle` 方法的開頭。
  - **結果格式化**: 目前的 `_format_sql_result` 寫死了純文字格式。可以考慮將其抽象成一個 `IResultFormatter` 介面，並根據結果的類型（例如，如果結果包含圖片URL，則可以格式化成圖片訊息）選擇不同的格式化策略。
