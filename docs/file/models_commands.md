# 檔案分析報告：`apps/bot/src/models/commands.py`

## 1. 檔案目的與角色

此檔案的目的是定義與指令處理相關的核心**資料結構**和**解析邏輯**。它扮演著一個小而關鍵的角色，處於使用者原始輸入和結構化指令處理之間的中間層。

它包含兩個主要部分：
1.  **`Command` dataclass**: 一個簡單的資料傳輸物件 (DTO)，用於將解析後的指令（包含名稱和參數）封裝起來，在系統的不同層之間傳遞。
2.  **`parse_command` 函式**: 一個實用函式，負責將來自聊天機器人的原始文字訊息，轉換為這個結構化的 `Command` 物件。

## 2. 主要類別/函數定義

### `Command` (dataclass)
一個非常直接的 `dataclass`，包含兩個欄位：
*   `name: str`: 指令的名稱（不含 `/`，小寫）。
*   `args: list[str]`: 一個包含指令所有參數的字串列表。

使用 `dataclass` 非常適合這種場景，因為它輕量且能自動產生必要的樣板程式碼，使得 `Command` 物件易於建立和使用。

### `parse_command(message: str) -> Command | None`
這是從原始訊息中提取指令的解析器。

**解析流程**:
1.  檢查訊息是否以 `/` 開頭。如果不是，則立即返回 `None`，表示這不是一個指令。
2.  將訊息按空格分割。
3.  提取第一部分作為指令名稱，移除開頭的 `/` 並轉換為小寫。
4.  **[關鍵問題]** 檢查指令名稱是否存在於一個**寫死的 `supported_commands` 列表中**。
5.  如果指令名稱不在該列表中，返回 `None`。
6.  如果存在，則將名稱和剩餘的參數打包成一個 `Command` 物件並返回。

## 3. 功能實現的簡要描述

這個模組的工作流程很簡單：
1.  `CommandExecutor` 收到一條原始訊息。
2.  它將訊息傳遞給 `parse_command`。
3.  `parse_command` 像一個**門衛**一樣工作：
    *   首先，它看訪客（訊息）是否佩戴了「/」徽章。沒有則不予理睬。
    *   然後，它取下訪客的名字，並在一個**過時的、手寫的訪客名單** (`supported_commands`) 上核對。
    *   如果名字在名單上，它就為訪客製作一張通行證（`Command` 物件），然後放行。
    *   如果名字不在名單上（即使這位訪客實際上是 VIP，例如 `/pg`），門衛也會因為名單沒更新而拒絕他。
4.  `CommandExecutor` 接收這個通行證（`Command` 物件）或 `None`，然後繼續後續處理。

## 4. 依賴關係

*   **`dataclasses.dataclass`**: 這是唯一的依賴，來自 Python 標準庫。該模組自給自足，不依賴專案中的任何其他服務。

## 5. 設計模式與架構決策

*   **資料傳輸物件 (DTO)**: `Command` 類別是一個典型的 DTO，其唯一目的是封裝和傳輸資料。
*   **關注點分離 (SoC) 的缺陷**: 理想情況下，解析器 (`parse_command`) 的關注點應該**僅僅是解析**——即從字串中提取結構化資料。然而，當前的實現將**解析**和**驗證**（檢查指令是否受支援）這兩個不同的關注點混在了一起。

## 6. 潛在的改進點

*   **核心問題：移除寫死的指令列表**:
    *   `supported_commands` 列表是**重複的知識來源**。系統中關於可用指令的**唯一事實來源 (Single Source of Truth)** 應該是 `CommandRegistry`。
    *   這個寫死的列表與實際註冊的指令（例如 `pg`）**已經不同步**，這會導致有效的指令被錯誤地拒絕。
    *   **重構建議**:
        1.  從 `parse_command` 中**完全移除** `supported_commands` 列表和相關的檢查邏輯。`parse_command` 的職責應簡化為：只要訊息以 `/` 開頭，就解析出 `Command` 物件。
        2.  將驗證指令是否存在的邏輯**移到 `CommandExecutor` 中**。在解析得到 `Command` 物件後，`CommandExecutor` 應使用 `CommandRegistry` 來檢查該指令是否真的有一個處理器與之對應 (`registry.get_handler(command.name)`)。
    *   這個重構將消除知識重複，修復潛在的錯誤，並使系統在新增或移除指令時更加健壯和易於維護。
