# 檔案分析報告：`apps/bot/src/services/nl_to_sql/services/query_statistics_service.py`

## 1. 檔案目的與角色

此檔案定義了 `QueryStatisticsService`，它是 NL-to-SQL 新架構的**監控與分析大腦**。它的角色並不是參與查詢的執行流程（如解析或建構），而是作為一個**被動的數據收集器和分析器**。

其核心職責是：
1.  **事件記錄器 (Event Recorder)**: 透過 `record_success` 和 `record_failure` 方法，從系統的其他部分（主要是解析器）接收關於操作結果的事件。
2.  **數據聚合器 (Data Aggregator)**: 在記憶體中對接收到的事件數據進行即時聚合，計算成功/失敗率、平均耗時、信心度分佈等核心指標。
3.  **效能分析師 (Performance Analyst)**: 不滿足於簡單的平均值，它還計算標準差、百分位數（P50, P90, P99），進行趨勢分析和效能評級，提供對系統行為的深度洞察。
4.  **健康監控中心 (Health Monitor)**: 提供 `get_service_health` 等方法，從高維度總結系統的整體健康狀況，如錯誤率、服務執行時間等。
5.  **數據提供者 (Data Provider)**: 透過 `get_stats`、`export_statistics` 等方法，將分析後的數據暴露給外部，可用於儀表板展示、日誌記錄或離線分析。

這個服務是系統的「黑盒子」，它默默記錄發生的一切，並能在需要時提供一份詳盡的診斷報告。

## 2. 主要類別/函數定義

### `class QueryStatisticsService(IStatistics)`
這是檔案中唯一定義的類別。它實現了 `IStatistics` 介面，這意味著任何需要記錄統計的元件都只與介面互動，而無需知道這個具體的實現細節。

#### 核心方法

*   **`__init__(self, max_history_size: int)`**:
    初始化各種用於儲存統計數據的資料結構，主要是 `defaultdict` 和一個有最大長度限制的 `deque`。`deque` 用於儲存詳細的歷史記錄，並能自動淘汰舊數據，防止記憶體無限增長。

*   **`record_success(self, ...)` 和 `record_failure(self, ...)`**:
    這是服務的兩個主要入口點，完全實現了 `IStatistics` 介面。它們的設計極具**防禦性**：
    *   **輸入驗證**: 對傳入的參數進行了大量的安全轉換（`_safe_..._conversion`）。
    *   **靜默失敗**: 將整個方法體包裹在 `try...except` 區塊中，即使記錄過程中發生錯誤，也只會記錄一條錯誤日誌，而不會將異常拋出，從而確保統計服務的穩定性不會影響到主應用的執行。

*   **`get_stats(self) -> dict`**:
    返回一個包含所有聚合統計數據的龐大字典。這是獲取最全面、最原始統計數據的方法。它會動態計算各種指標，如成功率、平均值、標準差、百分位數等。

*   **`get_service_health(self) -> dict`**:
    提供一個高層次的健康摘要，包括服務執行時間、總請求數、總體成功率、近期趨勢等，非常適合用於快速的健康檢查。

*   **`_categorize_error(self, error: str) -> str`**:
    一個輔助方法，使用正則表達式將詳細的錯誤訊息歸類為幾個預定義的類別（如 `Validation Error`, `Timeout`, `API Error`），這使得從宏觀上把握主要錯誤類型成為可能。

*   **`_grade_performance(self, ...)`**:
    一個有趣的分析功能，它不只給出冷冰冰的數字，而是根據耗時的百分位數給出一個人類可讀的評級（A, B, C, D, F），極大地增強了報告的可讀性。

## 3. 功能實現的簡要描述

`QueryStatisticsService` 的運作方式類似於一架飛機的**飛行數據記錄儀 (黑盒子)**：
1.  **被動監聽**: 它不安裝在駕駛艙，不影響飛機的飛行操作。它只是被動地接收來自引擎、舵面等各個系統的數據流（`record_success`/`record_failure`）。
2.  **即時處理**: 它在內部即時處理這些數據，將其分門別類地存入不同的記憶體區域（計數器、時間列表、歷史隊列）。
3.  **數據保護**: 即使數據流中出現一些雜訊或亂碼（無效的輸入），它的內建濾波器（`_safe_..._conversion`）也能確保記錄儀自身不會因此而崩潰。
4.  **事後分析**: 在飛行結束後（或在需要時），調查人員可以讀取記錄儀的數據（`get_stats`）。記錄儀不僅能提供原始數據，還能提供經過計算的分析報告（趨勢、效能評級），幫助人們了解飛機在整個航程中的詳細表現。

## 4. 依賴關係

*   **`structlog`**: 用於結構化日誌。
*   **`time`, `collections`, `datetime`**: Python 標準函式庫，用於時間處理和高效的數據結構。
*   **`..interfaces.statistics_interfaces.IStatistics`**: **實現**此介面，這是其與系統其他部分解耦的關鍵。

## 5. 設計模式與架構決策

*   **單一職責原則 (SRP)**: 這是此服務最核心的設計原則。它**只負責統計**，完全不參與任何業務邏輯。這種分離確保了業務邏輯的簡潔性和統計功能的獨立性與可重用性。
*   **觀察者模式 (Observer Pattern)**: 雖然沒有明確的註冊/通知機制，但其工作模式本質上是觀察者模式。`QueryStatisticsService` 是觀察者，而業務元件（如解析器）是主題。當主題狀態改變時（完成一次解析），它會「通知」（呼叫 `record_` 方法）觀察者。
*   **防禦性程式設計 (Defensive Programming)**: 整個類別是防禦性程式設計的典範。它預料到輸入可能不乾淨，並做好了應對準備，確保了自身的高可用性。
*   **資料驅動 (Data-Driven)**: 服務中的許多分析功能（如趨勢分析、評級）都是由收集到的數據驅動的，而不是基於硬編碼的規則。

## 6. 潛在的改進點

*   **持久化**: 目前所有數據都儲存在記憶體中，如果應用程式重啟，所有統計數據都會丟失。一個重要的改進是將統計數據定期（或在關閉時）持久化到檔案、資料庫或時序數據庫（如 InfluxDB, Prometheus）中。
*   **可配置性**: 許多內部閾值（如效能評級的標準、趨勢分析的時間窗口）都是硬編碼的。將這些值移到設定檔中可以使其更具靈活性。
*   **非同步記錄**: 雖然記錄操作本身很快，但在極高併發的場景下，可以考慮將記錄操作（特別是歷史記錄的寫入）放到一個非同步佇列中處理，以完全消除對主執行緒的任何潛在阻塞。
