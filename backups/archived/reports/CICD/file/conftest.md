### **【文件角色摘要】**

*   **📌 主要功能與責任：**
    此文件是 `pytest` 測試框架的**全局配置文件**，扮演著整個測試套件的「後勤中心」角色。其核心職責是：
    1.  **環境設置**: 在測試開始前，修改 `sys.path` 以確保能正確導入 `src` 目錄下的源碼。同時，它負責加載 `.env.test` 文件，為測試環境注入特定的環境變數。
    2.  **提供共享 Fixtures**: 定義一系列可被所有測試文件共享的 `pytest` fixtures。這些 fixtures 提供了各種被模擬的服務和客戶端（如 `mock_mcp_client`, `mock_database_service`）以及測試數據（如 `sample_line_event`）。
    3.  **資源管理**: 管理一些具有會話級生命週期的資源，最典型的例子是 `event_loop` fixture，它為所有異步測試提供了一個共享的、貫穿整個測試會話的 `asyncio` 事件循環。
    4.  **隔離與一致性**: 透過提供標準化的模擬對象，確保了不同測試文件在測試時所依賴的外部服務行為是一致的，從而增強了測試的穩定性和可重複性。

*   **🧠 在系統架構中的定位（上層來源與下游依賴）：**
    *   **定位**: 位於測試層的根部，是 `pytest` 框架自動發現和加載的核心配置文件之一。它不直接測試任何東西，而是為其他所有測試文件提供支持。
    *   **上層來源**: 由 `pytest` 測試框架在啟動時自動加載。
    *   **下游依賴**: 它不直接依賴任何生產代碼，但它導入的 `linebot`、`asyncpg` 等是被測代碼的依賴。它的主要下游是項目中所有的 `test_*.py` 文件，這些文件會使用它定義的 fixtures。

*   **🔁 是否處理通訊 / 外部互動：**
    否。絕大多數 fixtures 都是模擬的 (`Mock`, `AsyncMock`)。唯一的例外是 `real_db_connection`，它會嘗試建立一個真實的資料庫連接，但被設計為在連接失敗時跳過（`pytest.skip`），通常僅用於特定的整合測試。

*   **⚙️ 是否處理設定管理：**
    是。它在文件頂部處理 `sys.path` 的修改，並透過 `dotenv` 加載測試環境變數文件，是測試環境配置的中心。

*   **🧪 是否負責資料驗證、格式轉換或協定解析：**
    否。它只負責「提供」測試數據和模擬對象，不進行處理。

*   **💡 是否涉及平台相依性、跨平台兼容性、錯誤恢復：**
    *   **平台相依性**: 無。使用 `pathlib` 處理路徑，具有良好的跨平台性。
    *   **錯誤恢復**: `real_db_connection` fixture 中使用了 `pytest.skip`，這是一種優雅處理整合測試資源不可用情況的方式，避免了因環境問題導致整個測試套件失敗。

*   **🔐 是否與授權、安全、敏感操作有關：**
    是。它加載 `.env.test` 文件，其中可能包含測試用的 API Keys 或資料庫憑證。

*   **🎯 實用比喻：**
    `conftest.py` 就像一個大型演習的後勤補給站。在演習（運行測試）開始前，它負責：
    1.  **修路和掛路標**: 確保所有參演單位（測試文件）都能找到指揮部（`src` 源碼）。
    2.  **分發標準裝備**: 向每個單位分發一模一樣的模擬通訊設備（`mock_mcp_client`）、模擬後勤官（`mock_database_service`）和標準演習指令稿（`sample_line_event`）。
    3.  **提供公共設施**: 建立一個供所有單位使用的中央供電系統（`event_loop`）。
    這樣一來，無論哪個單位在哪個場地演練，他們使用的基礎設施和假想敵（模擬對象）都是標準化的，確保了演習結果的公平性和可比性。

### **【架構師補充面向】**

*   **🧪 可測試性：** 這個文件的存在本身就是為了提升整個項目的可測試性。它將測試的「準備」階段（Arrange）從各個測試用例中抽離出來，集中管理，大大減少了重複代碼，提高了測試代碼的可維護性。
*   **🗂️ 是否有循環相依 / 高耦合風險：** 無。`conftest.py` 的設計天然就是被依賴的，而不是去依賴別的測試模組。
*   **🧠 能否重構為 microservice 或 reusable package：** `conftest.py` 是 `pytest` 的特定機制，其概念不可重構成微服務。然而，其中定義的一些通用模擬（如果有的話）可以被提取到一個共享的測試工具庫中。
*   **⚠️ 潛在風險與改進建議：**
    *   **Fixture 過多**: 隨著項目變得複雜，`conftest.py` 可能會變得非常龐大。可以考慮將相關的 fixtures 按功能組織到不同的 `conftest.py` 文件中（例如，`tests/application/conftest.py`），`pytest` 支持這種層級化的配置。
    *   **路徑硬編碼**: 雖然使用了 `pathlib`，但 `src_path = Path(__file__).parent.parent / "apps" / "bot" / "src"` 這樣的路徑計算方式耦合了項目的目錄結構。如果項目結構改變，這裡需要手動更新。一個更健壯的方式是將項目安裝為可編輯模式 (`pip install -e .`)，這樣就不再需要手動修改 `sys.path`。
    *   **隱式依賴**: 測試文件會「神奇地」獲得這些 fixtures，對於不熟悉 `pytest` 的開發者來說，可能不清楚這些模擬對象是從哪裡來的。這是在 `pytest` 框架中便利性與明確性之間的一個權衡。
