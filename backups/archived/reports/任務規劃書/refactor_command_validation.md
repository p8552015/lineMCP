# 指令驗證邏輯重構任務規劃書

## 專案目標

## 🔍 透過 Serena 分析的關鍵發現

經過使用 Serena MCP Server 深入分析後，我們發現了以下關鍵問題：

### 當前架構的問題
1. **`models/commands.py` 中的靜態指令列表**：
   - 定義了一個硬編碼的 `supported_commands` 列表，包含 24 個指令名稱
   - 使用簡單的 `parse_command` 函數進行指令解析和驗證
   - 這個列表必須手動維護，與實際的 `CommandHandler` 實現不同步

2. **`CommandExecutor` 中的動態註冊機制**：
   - 在 `_register_all_commands()` 中硬編碼註冊了 7 個具體的 `CommandHandler`
   - 每個 `CommandHandler` 都有自己的 `command_name`, `description`, `aliases` 等元數據
   - 註冊表 (`CommandRegistry`) 管理所有處理器並提供查詢功能

3. **重複維護的問題**：
   - `models/commands.py` 列出了 24 個指令，但 `CommandExecutor` 只註冊了 7 個
   - 存在不同步的風險：新增指令時需要同時更新兩個地方
   - `parse_command` 可能會接受一個不存在處理器的指令

### 重構目標
本次重構將**移除 `models/commands.py` 的靜態驗證**，確立 `CommandExecutor` 的動態註冊表作為系統中唯一的指令定義來源，從而：
- 消除重複維護的成本
- 降低不一致的風險  
- 提升架構的優雅性與穩固性

### 🎯 實施策略
基於 Serena 分析結果，我們採用以下策略：
1. **最小化變更**：只移除 `parse_command` 的使用，保留 `CommandExecutor` 的現有架構
2. **向下相容**：確保所有已註冊的 7 個指令功能完全不變
3. **漸進式重構**：先實現新的解析方法，再移除舊的靜態文件
4. **充分測試**：每個步驟都通過 Serena 驗證和系統測試確保穩定性

## 🔧 執行規則

### 必須遵守的規則
1. **任務表區塊保護**：只能修改 `<!-- TASKS START -->` 與 `<!-- TASKS END -->` 之間的內容。
2. **狀態更新流程**：嚴格遵循 `TODO` -> `DOING` -> `DONE` / `BLOCKED` 的流程。
3. **即時保存**：每次狀態變更後立即保存此檔案。

### 程式碼品質要求
- **SOLID 原則**：所有新程式碼與重構後的程式碼必須符合 SOLID 設計原則。
- **向下相容**：重構過程中，對外提供的指令行為（參數、功能）應保持不變。
- **依賴檢查**：透過靜態分析與 `grep` 確認 `models/commands.py` 的所有引用都已被移除。

## 🧪 測試驗證流程

### 必要測試
1. **指令解析驗證**：
   - 測試新的 `parse_and_validate_command()` 方法能正確解析已註冊的 7 個指令
   - 驗證對未註冊指令的正確拒絕處理
   - 確認指令別名 (aliases) 的正確解析

2. **功能回歸測試**：
   - `/sql`: 測試 SQL 查詢功能，確保 SELECT 查詢正常執行
   - `/tables`: 驗證資料表列表和結構查詢功能 
   - `/status`: 確認系統狀態檢查功能
   - `/help`: 測試幫助訊息生成，確保顯示所有已註冊指令
   - `/info`, `/models`, `/postgres`: 驗證其他指令的正常執行

3. **系統整合測試**：
   - 透過 Serena 執行 `start-production.sh` 腳本啟動系統
   - 驗證 FastAPI 應用程式正常啟動，無錯誤日誌
   - 測試 Webhook 端點能正確接收和處理指令

4. **核心業務驗證**：
   - 模擬 LINE 用戶發送指令，驗證完整的處理流程
   - 測試自然語言查詢功能仍正常運作
   - 驗證錯誤處理和異常情況的正確處理

### 測試通過標準
- 所有單元測試與功能測試腳本 100% 通過。
- `start-production.sh` 腳本能成功啟動所有服務，無錯誤日誌。
- 核心功能驗證中的所有指令都能返回正確、符合預期的結果。

## ⚠️ 錯誤處理機制

### 當任務失敗時
1. 將失敗任務的狀態設為 `BLOCKED`。
2. 在該任務的「描述」欄位中，使用 `(原因：具體錯誤描述)` 格式註記失敗原因。
3. 立即暫停後續所有任務的執行，直到阻塞問題解決。
4. 分析日誌、程式碼，定位問題根本原因。
5. 在解決問題後，將狀態改回 `DOING` 並繼續執行。
