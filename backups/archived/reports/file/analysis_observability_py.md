## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案是應用程式的**可觀測性 (Observability) 基礎設施層**。它負責在應用程式啟動時，集中設定和初始化所有與監控、偵錯和效能分析相關的服務。
  - **核心職責**：
    1.  **結構化日誌設定**: 透過整合 `structlog` 函式庫，將傳統的純文字日誌升級為**機器可讀的 JSON 格式日誌**。這使得日誌的過濾、查詢和分析變得極其高效。
    2.  **分散式追蹤設定**: 透過整合 `OpenTelemetry` (OTel)，為應用程式提供了**分散式追蹤**的能力。這對於理解一個請求在微服務架構中的完整生命週期至關重要。
    3.  **智慧型導出器配置**: `_setup_telemetry_exporter` 方法實現了一個**智慧型、帶容錯的**導出器 (Exporter) 設定邏輯。它會：
        -   首先嘗試連接使用者明確配置的 OTLP (OpenTelemetry Protocol) 端點。
        -   如果沒有配置，它會**自動探測**常見的端點（如 `localhost`, `jaeger`）。
        -   如果遠端端點都不可用，它會優雅地**降級**到在控制台輸出追蹤資訊（僅限開發環境）。
        -   這種設計極大地提升了在不同環境中設定的便利性和健壯性。
    4.  **自動化儀表 (Auto-Instrumentation)**: 自動為 `httpx` 客戶端庫添加追蹤儀表，這意味著所有使用 `httpx` 發出的 HTTP 請求都會被自動包含在追蹤鏈路中。

- 🧠 **在系統架構中的定位**:
  - **定位**：這是一個典型的**橫切關注點 (Cross-Cutting Concern)**。日誌和追蹤不是核心業務邏輯，但它們是所有業務邏輯都需要的基礎功能。這個模組在應用程式啟動時（通常在 `main.py`）被呼叫一次，然後其效果（如可用的 `logger` 和 `tracer`）會貫穿整個應用程式。
  - **上層來源**：`main.py` 或應用程式的啟動腳本。
  - **下游依賴**：`structlog`, `opentelemetry-*` 系列函式庫，以及應用的設定模組 `src.config`。

- 🎯 **實用比喻**:
  - `observability.py` 就像是為一座大樓安裝**完整的監控系統**。
    -   `structlog.configure` 相當於為大樓的每個房間都安裝了**帶有標準化接口的感應器**（溫度、濕度、煙霧），所有數據都以統一的 JSON 格式上報。
    -   `trace.set_tracer_provider` 則相當於安裝了一個**中央監控中心和錄影系統**。
    -   `_setup_telemetry_exporter` 是智慧型的**警報系統**。它會優先嘗試將錄影（追蹤數據）傳送到總部的安全中心（OTLP 端點）。如果網路不通，它會嘗試連接本地的警衛室（自動探測的端點）。如果連警衛室都連不上，它至少會把影像顯示在本地的螢幕上（控制台導出器），而不是直接罷工。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 這個檔案主要由**函式 (Functions)** 組成，而不是類別，這對於一個一次性設定的配置模組來說是合適的。
- 函式名稱：`setup_observability()`
  - 📌 **創建目的**: 作為**單一的入口點**，封裝了所有設定可觀測性的複雜步驟。外部呼叫者只需呼叫這一個函式，即可完成所有設定。
  - 🧩 **內含哪些關鍵方法與邏輯功能**:
    -   首先設定 `structlog`。
    -   然後，如果啟用了 OpenTelemetry，則繼續設定 `TracerProvider` 和資源。
    -   最關鍵的是，它呼叫 `_setup_telemetry_exporter` 來處理複雜的導出器邏輯。
    -   最後，它啟用 `HTTPXClientInstrumentor`。
    -   整個函式充滿了 `try...except` 區塊，確保即使部分功能（如 OTel）設定失敗，也不會導致整個應用程式啟動失敗，極具彈性。
- 函式名稱：`_setup_telemetry_exporter()`
  - 📌 **創建目的**: **將導出器的選擇邏輯從主設定流程中分離出來**，使其成為一個獨立的、可測試的單元。這是**單一職責原則**的良好體現。
  - 💡 **設計考量**:
    - **網路可用性檢查**: `_check_otlp_endpoint_availability` 函式在嘗試連接一個遠端端點之前，先用一個簡單的 `socket` 連接來檢查其可用性。這避免了在應用程式啟動時因為等待一個不存在的端點而導致的長時間卡頓，極大地改善了開發體驗。
    - **漸進式增強**: 整個設定流程是可選的。使用者可以透過設定 (`settings.otel_enabled`) 完全禁用 OTel，只使用結構化日誌，這使得該模組可以被輕易地整合到不同需求的專案中。
- 函式名稱：`get_telemetry_health()`
  - 📌 **創建目的**: 提供一個**自我診斷**的介面，讓外部（如一個 `/status` 端點）可以查詢可觀測性系統自身的健康狀況。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。該模組只依賴於設定物件和幾個知名的函式庫，與應用程式的其他業務邏輯完全解耦。
- 🧪 **可測試性**：**高**。
    -   可以透過在測試中設定不同的 `settings` 值，來驗證 `setup_observability` 的行為。
    -   可以輕易地對 `_check_otlp_endpoint_availability` 進行 Mock，來模擬 OTLP 端點可用或不可用的情況，並斷言 `_setup_telemetry_exporter` 是否選擇了正確的降級策略。
- 🧠 **設計優點**:
  - **健壯性與彈性**: 大量的 `try...except` 和對功能的選擇性啟用，使得這個模組非常健壯。
  - **開發者體驗**: 自動探測和降級到控制台的功能，極大地簡化了開發者的本地設定工作。
  - **業界最佳實踐**: 完全基於 `structlog` 和 `OpenTelemetry` 這兩個開放標準和廣泛使用的函式庫，避免了廠商鎖定，並易於與各種後端監控平台（如 Jaeger, Datadog, New Relic）整合。
