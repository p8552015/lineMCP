## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `HelpCommandHandler` 類別，是處理 `/help` 指令的具體實作。
  - **核心職責**：作為系統的**動態文件生成器**和**使用者指南**。它有兩種操作模式：
    1.  **通用幫助 (`/help`)**: 當不帶參數時，它會從**指令註冊表 (`CommandRegistry`)** 動態獲取所有已註冊的指令，並將它們的用法、描述和別名格式化成一個對使用者友善的列表。
    2.  **特定指令幫助 (`/help <command_name>`)**: 當帶有指令名稱作為參數時，它會從註冊表中查找該特定指令的處理器，並顯示其詳細的用法說明。它還會從一個內部字典 (`extra_help_map`) 中查找並附加上額外的、更詳細的說明文字。

- 🧠 **在系統架構中的定位**:
  - **定位**：在 `commands` 模組中，它是一個**元指令 (Meta-Command)**，它的功能是描述系統中所有其他的指令。它是指令子系統的「使用說明書」。
  - **上層來源**：由 `CommandExecutor` 在解析到 `/help` 指令時調用。
  - **下游依賴**：`CommandRegistry`。這是它最關鍵的依賴，它透過 `get_command_registry()` 函式來獲取全域的指令註冊表實例，從而實現動態幫助生成。

- 🎯 **實用比喻**:
  - `HelpCommandHandler` 就像是軟體應用程式中的**「幫助」選單**。點擊頂層的「幫助」會彈出一個總覽視窗，列出所有主要功能（`/help`）。如果你想了解某個特定功能的詳細用法，比如「如何使用合併儲存格」，你可以點擊對應的子選單，系統會彈出一個專門解釋這個功能的詳細說明視窗（`/help <feature_name>`）。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`HelpCommandHandler`
- 📌 **創建目的**:
  - **核心目的**：**提升系統的可發現性 (Discoverability) 和易用性 (Usability)**。讓使用者無需閱讀外部文件，就能在應用程式內部自行學習如何使用所有功能。
  - **具體目的**：
    1.  為新使用者提供一個入門指引。
    2.  為老使用者提供一個忘記指令時的快速參考。
    3.  確保幫助文件與實際功能**永遠同步**。
- 🧭 **使用場景**:
  - 新使用者第一次與機器人互動時。
  - 使用者忘記了某個指令的確切名稱或參數時。
  - 開發者新增了一個新指令後，想確認它是否已正確註冊並顯示在幫助列表中時。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `handle()`: 判斷有無參數，並分發到 `_get_all_commands_help` 或 `_get_specific_command_help`。
  - `_get_all_commands_help()`: 核心動態幫助生成邏輯。它呼叫 `get_command_registry().list_commands()` 來獲取所有指令處理器的實例列表，然後遍歷這個列表，動態地從每個處理器實例中提取 `command_name`, `description`, `aliases` 等屬性來建構幫助訊息。
  - `_get_specific_command_help()`: 從註冊表中按名稱獲取單個處理器，並顯示其詳細資訊。
  - `_get_extra_help()`: 一個私有的輔助方法，包含了一個**硬編碼 (Hard-coded)** 的字典，為特定指令提供更豐富的、帶有範例的額外說明。
- 💡 **設計考量**:
  - **自省與反射 (Introspection/Reflection)**: 這是此類別最出色的設計。它不是靜態地維護一份幫助文件，而是**在執行期去「詢問」指令註冊表**：「你現在有哪些指令？每個指令的功能是什麼？」這保證了只要一個指令被成功註冊到 `CommandExecutor`，它就**自動地**會出現在 `/help` 列表裡，完全無需手動更新幫助文件。這大大降低了維護成本，並避免了文件與功能脫節的問題。
  - **關注點分離**: 將通用的、可以從指令本身屬性中獲取的資訊（如名稱、描述）和那些需要額外說明的、更詳細的資訊（`_get_extra_help` 中的內容）分開處理。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**極低**。它與 `CommandRegistry` 緊密耦合，但這是一種設計上的、刻意的、健康的耦合。
- 🧪 **可測試性**：**高**。在測試開始前，可以手動向 `CommandRegistry` 註冊幾個 Mock 的指令處理器。然後呼叫 `HelpCommandHandler`，斷言它生成的幫助訊息是否正確地反映了這幾個 Mock 指令的資訊。
- 🧠 **重構潛力**:
  - **將額外幫助資訊移入指令本身**: `_get_extra_help` 中的字典是硬編碼的，這意味著每當新增或修改一個需要詳細說明的指令時，都必須記得來修改 `HelpCommandHandler`。這破壞了幫助系統的動態性。一個更好的設計是將這段「額外幫助文字」也作為一個屬性或方法（例如 `get_detailed_help()`）添加到 `CommandHandler` 的抽象基底類別中。這樣，每個指令就可以自己攜帶自己的詳細說明，`HelpCommandHandler` 只需檢查並呼叫這個新方法即可，完全無需再維護那個硬編碼的字典。
  - **幫助訊息格式化**: 目前是手動拼接字串。未來如果需要更複雜的幫助格式（例如，在支援的平台上顯示為卡片訊息），可以將格式化的邏輯抽取到一個獨立的 `HelpFormatter` 類別中。
