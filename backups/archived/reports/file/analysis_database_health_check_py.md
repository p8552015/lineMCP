## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `DatabaseHealthChecker` 類別，其核心職責是**從應用程式的角度**，對目標資料庫進行一次**全面的、多維度的健康體檢**。
  - **核心職責**：它將「健康」定義為三個層次：
    1.  **第一層：連通性 (Connectivity)**: 這是最基礎的檢查。`check_connection` 方法會嘗試連接資料庫並執行一個 `SELECT 1` 查詢。它還內建了**自動重試機制**，以應對網路瞬時抖動。
    2.  **第二層：結構一致性 (Schema Consistency)**: `_check_tables_new` 方法的核心是**驗證資料庫的結構是否符合應用程式的期望**。它會檢查所有業務邏輯所**依賴的核心資料表**（如 `machines`, `orders`）是否存在。這一步驟確保了資料庫的 Schema 沒有發生意外的、破壞性的變更。
    3.  **第三層：功能可用性 (Functionality)**: `_check_functionality` 方法更進一步，它會執行一些**代表性的 `SELECT` 唯讀查詢**，來模擬應用程式的真實操作。這可以捕獲一些更深層次的問題，例如資料表存在但權限不正確，或者索引損壞導致查詢失敗。

- 🧠 **在系統架構中的定位**:
  - **定位**：這是一個**應用程式層的診斷工具**。它不應該在每個 API 請求中被呼叫，而是用於特定的診斷場景：
    -   在**應用程式啟動時**（由 `startup_health_check.py` 呼叫），執行一次快速檢查，確保資料庫已準備就緒。如果檢查失敗，可以阻止應用程式啟動，實現**快速失敗 (Fail-fast)**。
    -   在一個**專門的 `/health` 或 `/status` API 端點**中被呼叫，供維運人員或自動化監控系統查詢資料庫的詳細健康狀況。
  - **上層來源**：`startup_health_check.py`，或 `/status` 指令處理器。
  - **下游依賴**：`asyncpg` 函式庫。值得注意的是，它**直接使用 `asyncpg`**，而不是透過 SQLAlchemy 或其他 ORM，這使得它可以更精確地控制執行的 SQL 並減少外部依賴。

- 🎯 **實用比喻**:
  - `DatabaseHealthChecker` 就像是飛機起飛前的**機務工程師**。在允許飛機（應用程式）起飛前，他會執行一套嚴格的檢查清單：
    1.  **檢查油路是否通暢** (`check_connection`)。
    2.  **檢查所有關鍵部件（機翼、引擎、起落架）是否都在正確的位置上** (`_check_tables_new`)。
    3.  **啟動引擎並檢查儀表板上的讀數是否正常** (`_check_functionality`)。
    -   只有當所有檢查都通過（或僅有不影響安全的警告）時，機務工程師才會簽字放行，允許飛機進入跑道。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`DatabaseHealthChecker`
  - 📌 **創建目的**: 將與「驗證資料庫狀態」相關的所有複雜邏輯**封裝**在一個地方。如果沒有這個類別，這些檢查邏輯可能會散落在應用程式的多個地方，難以維護。
  - 🧩 **內含哪些關鍵方法與邏輯功能**:
    - `__init__()`: 接收資料庫 URL。最重要的是，它在**類別內部硬編碼了 `required_tables` 這個資料結構**。這是整個類別的核心，它定義了應用程式與資料庫之間的「契約」。
    - `comprehensive_health_check()`: 作為**公開的入口點**，它按照「連通性 -> 結構 -> 功能」的順序，依次呼叫各個私有的檢查方法，並將結果匯總成一份詳細的、結構化的 JSON 報告。
    - `_check_tables_new()`: 透過查詢 `information_schema.tables` 來獲取資料庫的元資料，並與 `required_tables` 進行比較。
    - `_check_functionality()`: 執行硬編碼的 `SELECT` 查詢來測試功能。
  - 💡 **設計考量**:
    - **應用程式中心的視角**: 這個檢查器的設計完全是從「我的應用程式需要什麼」出發，而不是從「資料庫有什麼」出發。`required_tables` 的定義就是這種思想的體現。
    - **詳細的診斷輸出**: 返回的不是一個簡單的 `True/False`，而是一個**詳細的、結構化的字典**。這對於問題排查極其有用。當檢查失敗時，開發者可以從返回的 JSON 中精確地知道是哪個環節（連接、缺表、功能查詢）出了問題。
    - **無狀態**: 該類別本身是無狀態的，使其可以被安全地在多個非同步任務中共享和重用。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**中等**。這個類別與**特定的資料庫 Schema**（`required_tables` 的定義）是**緊密耦合**的。這在這種場景下是**不可避免且完全可以接受的**，因為它的職責本身就是去驗證這個特定的 Schema。當 Schema 發生變更時（例如，新增一個 `users` 表），開發者**必須**同步更新 `required_tables` 的定義。這種耦合是**有意為之**的，它迫使開發者在修改 Schema 的同時，也去更新應用程式的健康檢查邏輯。
- 🧪 **可測試性**：**高**。在單元測試中，可以：
    -   為 `__init__` 傳入一個指向測試資料庫的 URL。
    -   使用 `mock.patch` 來模擬 `asyncpg.connect`，使其返回一個 Mock 的 Connection 物件。
    -   控制這個 Mock Connection 的 `fetchval` 和 `fetch` 方法的返回值，來模擬各種場景（如連接失敗、找不到表、查詢失敗等），並斷言 `comprehensive_health_check` 返回的 JSON 報告是否符合預期。
- 🧠 **設計優點**:
  - **分層檢查**: 「連接 -> 結構 -> 功能」的分層檢查邏輯非常清晰和健壯。
  - **快速失敗**: 如果連接失敗，它會立即返回，不會繼續執行後續的檢查，提高了效率。
  - **契約強制**: 它在程式碼層面強制了應用程式對資料庫 Schema 的依賴關係，使得這種隱性的「契約」變得明確。
