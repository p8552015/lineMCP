## 🧩 樣板 1：檔案在專案中扮演的角色

【文件角色摘要】
- 📌 **主要功能與責任**:
  - 此檔案定義了 `RuleBasedParser` 類別，它是 `CompositeParser` 管理的**具體解析策略之一**。
  - **核心職責**：
    1.  **模式匹配**: 使用預先定義好的**正則表達式**和**關鍵字**來匹配使用者輸入的自然語言文本。
    2.  **快速路徑處理 (Fast Path)**: 專門用於快速、高效地處理結構化、高頻的查詢，例如「M123狀態」、「查詢加工部」等。
    3.  **參數提取**: 對於匹配成功的查詢，從文本中提取具體的參數（如機器ID、部門名稱、時間範圍等）。
    4.  **結構化輸出**: 將解析結果封裝成一個結構化的 `ParsedQuery` 物件，其中包含查詢的類型 (`QueryType`) 和提取出的參數，但**不包含**最終的 SQL 語句。

- 🧠 **在系統架構中的定位**:
  - **定位**：在 NL-to-SQL 子系統的解析層中，它是一個**具體的、基於規則的解析引擎**。它通常是 `CompositeParser` 中的第一個或優先級最高的策略，因為它的執行成本遠低於 AI 解析器。
  - **上層來源**：由 `CompositeParser` 根據其 `can_handle` 方法的回傳值來決定是否呼叫它。
  - **下游依賴**：
    - `IConfiguration`: 依賴於設定服務來獲取查詢模式的設定檔 (`query_patterns.yaml`)。這使得規則的擴展無需修改程式碼。
    - 它不依賴任何其他服務，是一個相對獨立的計算單元。

- 🔐 **是否與授權、安全、敏感操作有關**:
  - **否**。它只負責文本的模式匹配和解析。

- 🎯 **實用比喻**:
  - 如果說 `CompositeParser` 是醫院的主治醫生，那麼 `RuleBasedParser` 就是醫院的**導診護士**。她能快速處理大量常見問題，比如「掛號處在哪裡？」、「幾點可以探病？」等。她根據一本手冊（規則配置）來快速回答，無需驚動昂貴的專家醫師（AI 解析器）。只有當遇到手冊上沒有的疑難雜症時，她才會將病人轉介給主治醫生。

## 🧩 樣板 2：有哪些類別，以及創建目的與結構特性

【類別分析】
- 類別名稱：`RuleBasedParser`
- 📌 **創建目的**:
  - **核心目的**：提供一種**高效、低成本、可預測**的自然語言解析方案，專門用於處理固定的查詢模式。
  - **具體目的**：
    1.  降低對昂貴 AI/LLM 服務的依賴和呼叫次數，節省成本和響應時間。
    2.  確保對特定、重要查詢的解析結果是 100% 準確和穩定的，不受 AI 模型不確定性的影響。
- 🧭 **使用場景**:
  - 由 `EnhancedServiceFactory` 創建，並在初始化時注入一個 `IConfiguration` 實例。
  - 被 `CompositeParser` 作為一個策略添加進去。
  - 當使用者輸入的文本匹配到預設規則時，其 `parse` 方法被呼叫。
- 🧩 **內含哪些關鍵方法與邏輯功能**:
  - `__init__(...)`: 接收配置服務，並從中載入正則表達式模式。
  - `parse()`: 核心解析邏輯，按優先級遍歷所有規則，進行匹配。
  - `can_handle()`: 快速評估輸入文本是否符合任何已知規則，並返回一個信心度分數。這是 `CompositeParser` 進行策略選擇的依據。
  - `_create_*_query()`: 一系列私有輔助方法，用於創建結構化的 `ParsedQuery` 回傳物件。
  - `_extract_type_specific_parameters()`: 用於從文本中提取特定查詢類型所需的參數。
- 🔄 **是否支援擴充或注入**:
  - **是**，但方式不同。它不是被注入，而是**依賴注入**。其擴展性體現在**配置驅動**上：可以透過修改 `query_patterns.yaml` 設定檔來新增或修改規則，而**無需修改一行 Python 程式碼**。這完美地體現了**開閉原則**。
- 💡 **設計考量**:
  - **配置驅動 (Configuration-Driven)**: 將易變的規則與穩定的解析邏輯分離，極大提高了可維護性和擴展性。
  - **單一職責原則 (SRP)**: 職責非常清晰，只做基於規則的解析。SQL 的生成被明確地留給了後續的 `QueryBuilder`。
  - **里氏替換原則 (LSP)**: 嚴格遵守 `IParser` 介面的約定，使得 `CompositeParser` 可以無差別地對待它和 `AIEnhancedParser`。

## 🧱 額外架構師視角建議補充欄位

- 🗂️ **高耦合風險**：**低**。它與具體的規則實現解耦（透過設定檔），只依賴於抽象的配置介面。
- 🧪 **可測試性**：**極高**。由於其行為是確定的（輸入相同，輸出永遠相同），測試非常簡單。只需為其注入一個 Mock 的 `IConfiguration`，提供測試用的規則，然後就可以驗證其解析和參數提取邏輯是否正確。
- 🧠 **重構潛力**:
  - 目前的設計已經相當不錯。
  - 一個可能的優化方向是，如果規則變得非常複雜，可以考慮引入一個更強大的規則引擎或語法解析庫（如 ANTLR），而不是手動管理大量的正則表達式。
  - 另一個方向是，建立一個**規則編輯和測試的視覺化界面**，讓非開發人員（如產品經理或運維人員）也能夠安全地新增和修改查詢規則。目前的配置驅動設計為此打下了良好的基礎。
