# MyPy 錯誤根本原因深度分析報告

## 🔍 核心問題根源

### 1. 架構層面問題

#### 動態類型系統與靜態類型檢查衝突
- **問題**: 專案大量使用動態類型 (`dict[str, Any]`)，與 MyPy 靜態類型檢查不兼容
- **根本原因**: 四層架構設計中的依賴注入模式導致類型推理困難
- **影響範圍**: 107 個錯誤中約 60% 源於此問題

#### 聯合類型處理不當
- **問題**: `Optional` 類型和聯合類型 `|` 使用不一致
- **根本原因**: 代碼庫從舊版 Python 類型語法遷移不完整
- **具體表現**: `str | None` 與 `Optional[str]` 混用

### 2. 具體錯誤類型根因

#### Assignment 錯誤 (22個) - 高優先級
**根本原因**: 類型推理失敗與動態配置系統
```python
# 問題代碼模式
parameters = {}  # MyPy 推理為 dict[str, Any]
parameters["days"] = 30  # int 賦值給 Any，但期望 str
```
**解決策略**: 
- 使用明確的類型註解
- 分離配置與業務邏輯

#### Valid-Type 錯誤 (15個) - 架構問題
**根本原因**: 使用 `callable` 作為類型註解
```python
# 錯誤使用
def _build_parameter_validators(self) -> dict[QueryType, callable]:
# 應該使用
def _build_parameter_validators(self) -> dict[QueryType, Callable[..., Any]]:
```

#### Misc 錯誤 (18個) - 邏輯缺陷
**根本原因**: 函數路徑分析不完整
- 缺少 return 語句
- 邏輯分支覆蓋不全

### 3. 系統性問題模式

#### 依賴注入模式的類型安全問題
- **問題**: `get_service()` 方法返回 `Any`，破壞類型鏈
- **根本原因**: 服務註冊使用動態類型映射
- **影響**: 導致下游所有使用該服務的代碼類型推理失敗

#### 配置驅動的動態類型問題
- **問題**: JSON 配置解析產生 `object` 類型
- **根本原因**: 沒有為配置數據建立 TypedDict 或 Pydantic 模型
- **具體案例**: `pattern_info["min_length"]` 推理為 `object`

#### 錯誤處理模式不一致
- **問題**: 異常類型返回值不一致
- **根本原因**: 沒有統一的錯誤處理類型規範
