# 錯誤分析與解決流程樣板

## 📋 概述

本樣板基於 PostgreSQL MCP Cancel Scope 問題的深刻教訓而制定，旨在防止重複犯下**過度工程化**、**架構分析不足**和**盲目重新實現**的錯誤。

**核心原則**：
- 🔍 **理解優於實現**
- 🎯 **簡單優於複雜**
- 🧪 **測試勝過假設**
- 📊 **分析先於編碼**

---

## 🚨 強制檢查點系統

### ⛔ 紅色停止信號
如果遇到以下情況，**立即停止當前方向**：
- [ ] 測試失敗超過 2 次
- [ ] 實施時間超過預估的 200%
- [ ] 解決方案複雜度超過問題本身
- [ ] 無法在 5 分鐘內解釋解決方案給他人
- [ ] 發現現有工作解決方案

### 🟡 黃色警告信號  
如果遇到以下情況，**重新評估方向**：
- [ ] 需要創建超過 3 個新檔案
- [ ] 需要引入新的外部依賴
- [ ] 解決方案涉及多個系統組件
- [ ] 測試覆蓋率低於 80%
- [ ] 無法找到類似問題的解決案例

## 階段一：問題定義與現狀分析 📊

### 1.1 問題定義檢查清單
```markdown
## 問題陳述
- [ ] **現象描述**：具體錯誤訊息、重現步驟、影響範圍
- [ ] **發生頻率**：每次/偶爾/特定條件下
- [ ] **影響評估**：功能性/性能/安全性/用戶體驗
- [ ] **緊急程度**：生產中斷/功能缺陷/改進需求

## 問題邊界
- [ ] **範圍界定**：影響的系統模組、檔案、功能
- [ ] **非問題確認**：明確不是問題的部分
- [ ] **相關性評估**：是否與其他已知問題相關
```

### 1.2 現狀調研檢查清單
```markdown
## 📂 代碼庫檢查
- [ ] **搜索相關檔案**：關鍵字搜索所有相關實現
- [ ] **依賴關係映射**：誰調用誰，誰依賴誰
- [ ] **歷史變更分析**：git log 檢查相關變更歷史
- [ ] **測試用例檢查**：現有測試覆蓋和通過狀態

## 🌐 外部資源調研
- [ ] **官方文檔**：相關技術棧的官方文檔
- [ ] **GitHub Issues**：開源項目的已知問題
- [ ] **Stack Overflow**：社群解決方案
- [ ] **技術博客**：最佳實踐和經驗分享
```

### 1.3 架構分析檢查清單
```markdown
## 🏗️ 系統架構理解
- [ ] **繪製架構圖**：當前系統組件關係圖
- [ ] **數據流分析**：數據如何在系統中流動
- [ ] **錯誤傳播路徑**：錯誤如何在系統中傳播
- [ ] **關鍵路徑識別**：影響核心功能的路徑

## 📋 依賴關係分析
- [ ] **直接依賴**：直接使用的庫、模組、服務
- [ ] **間接依賴**：傳遞性依賴關係
- [ ] **循環依賴檢查**：是否存在循環依賴
- [ ] **版本相容性**：依賴版本的相容性問題
```

```markdown
## 🔍 內部解決方案

- [ ] **社群方案**：論壇、討論區的解決方案
- [ ] **官方建議**：技術提供商的官方建議
```

### 2.2 解決方案可行性評估
```markdown
## 💰 成本評估
- [ ] **開發時間**：預估實施時間（小時/天）
- [ ] **測試時間**：預估測試和驗證時間
- [ ] **維護成本**：長期維護的複雜度和成本
- [ ] **學習成本**：團隊學習新技術的成本

## ⚖️ 風險評估
- [ ] **技術風險**：新技術的穩定性和成熟度
- [ ] **架構風險**：對現有架構的影響
- [ ] **數據風險**：對數據完整性的影響
- [ ] **回滾風險**：實施失敗時的回滾難度

## 🎯 效益評估
- [ ] **問題解決度**：解決方案完全/部分解決問題
- [ ] **性能改善**：對系統性能的影響
- [ ] **可擴展性**：未來擴展的可能性
- [ ] **代碼品質**：對整體代碼品質的影響
```

## 階段三：解決方案設計 🎨

### 3.1 解決方案比較矩陣
```markdown
| 方案 | 複雜度 | 實施時間 | 風險 | 維護成本 | 問題解決度 | 推薦度 |
|------|--------|----------|------|----------|------------|--------|
| 方案A | 低/中/高 | X小時 | 低/中/高 | 低/中/高 | X% | ⭐⭐⭐⭐⭐ |
| 方案B | 低/中/高 | X小時 | 低/中/高 | 低/中/高 | X% | ⭐⭐⭐⭐⭐ |
| 方案C | 低/中/高 | X小時 | 低/中/高 | 低/中/高 | X% | ⭐⭐⭐⭐⭐ |
```

### 3.2 設計原則檢查
```markdown
## 🎯 KISS 原則檢查 (Keep It Simple, Stupid)
- [ ] **最簡解決方案**：是否選擇了最簡單的可行方案
- [ ] **複雜度合理性**：複雜度是否與問題規模匹配
- [ ] **可理解性**：其他開發者能在 5 分鐘內理解

## 🔧 YAGNI 原則檢查 (You Aren't Gonna Need It)
- [ ] **當前需求focus**：是否只解決當前問題
- [ ] **避免過度設計**：沒有為未來可能的需求過度設計
- [ ] **功能精簡**：只包含必要的功能

## 🏗️ 架構一致性檢查
- [ ] **現有模式遵循**：與現有代碼風格和模式一致
- [ ] **命名規範**：遵循專案的命名規範
- [ ] **依賴管理**：不引入不必要的依賴
```

## 🚨 常見錯誤防護機制

### 過度工程化防護
```markdown
## ⚠️ 警告信號
- [ ] 解決方案比問題複雜
- [ ] 需要學習新的複雜技術
- [ ] 實施時間超過 1 天
- [ ] 涉及重新設計現有架構

## 🛡️ 防護措施
- [ ] **強制簡化**：每次都問"有更簡單的方法嗎？"
- [ ] **時間盒限制**：設定嚴格的時間限制
- [ ] **同儕審查**：讓其他人評估複雜度
- [ ] **回到原點**：定期重新評估問題定義
```

### 架構混亂防護
```markdown
## ⚠️ 警告信號
- [ ] 命名衝突
- [ ] 循環依賴
- [ ] 多個實現同一功能
- [ ] 不清楚的責任邊界

## 🛡️ 防護措施
- [ ] **架構圖維護**：及時更新架構圖
- [ ] **命名規範**：嚴格的命名規範
- [ ] **責任劃分**：清晰的責任劃分
- [ ] **定期重構**：定期清理冗餘代碼
```

### 測試忽視防護
```markdown
## ⚠️ 警告信號
- [ ] 測試覆蓋率低於 80%
- [ ] 測試持續失敗但被忽略
- [ ] 手動測試為主
- [ ] 沒有回歸測試

## 🛡️ 防護措施
- [ ] **測試優先**：測試失敗時立即停止
- [ ] **自動化測試**：儘可能自動化測試
- [ ] **持續整合**：CI/CD 管道的測試門檻
- [ ] **測試評審**：測試案例的同儕評審
```

## 📝 模板使用指南

### 如何使用此模板
1. **複製模板**：為每個問題創建此模板的副本
2. **填寫檢查清單**：逐項填寫所有檢查清單
3. **記錄決策**：記錄重要的決策和理由
4. **追蹤進度**：使用檢查清單追蹤進度
5. **事後回顧**：問題解決後進行回顧

### 模板客製化
- **專案特定**：根據專案特性客製化檢查項目
- **團隊約定**：加入團隊特定的約定和標準
- **工具整合**：與現有工具和流程整合
- **持續改進**：基於使用經驗持續改進模板

## 🏆 成功案例模式

### 配置問題模式
```
問題：系統行為異常
調研：檢查配置檔案和環境變數
發現：配置使用了錯誤的值
解決：修改一行配置
時間：5 分鐘
```

### 依賴衝突模式
```
問題：功能無法正常工作
調研：檢查依賴關係和版本
發現：版本衝突或依賴缺失
解決：更新或安裝正確的依賴
時間：30 分鐘
```

### 邏輯錯誤模式
```
問題：計算結果不正確
調研：檢查演算法和邊界條件
發現：邊界條件處理錯誤
解決：修正邏輯判斷
時間：1-2 小時
```
